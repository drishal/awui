# Architecture

How the server is put together: the module map, the adapter registry, how each harness is driven, and how approvals reach a card. Adding a harness has its own guide in [harnesses.md](harnesses.md).

```
browser ──HTTP/SSE──▶ Node server (127.0.0.1:4783) ──▶ HarnessAdapter
                                                        ├─ Pi     (child process: `pi --mode rpc`, one per live chat)
                                                        ├─ omp    (child process: `omp --mode rpc-ui`, one per live chat)
                                                        ├─ Hermes (child process: `python -m tui_gateway.entry`, one per live chat)
                                                        ├─ Claude Code (child process: `claude -p` in stream-json mode, one per live chat)
                                                        ├─ Codex   (child process: `codex app-server`, one per live chat)
                                                        ├─ OpenCode (one private `opencode serve` for every chat: its HTTP API and event stream)
                                                        ├─ Grok   (child process: `grok agent --no-leader stdio`, one per live chat)
                                                        ├─ DSH    (child process: `dsh --profile acp`, one per live chat)
                                                        ├─ Awui   (`pi --mode rpc`, read-only: the writing/executing tools denied)
                                                        └─ fake   (tests only)
```

**Project isolation.** `Workspaces.open` and every `Workspaces.get` re-resolve the realpath; a replaced project directory cannot quietly point elsewhere and remain an approved workspace. `ManagedWorktrees` creates separate real checkouts under `.awui/worktrees` inside that validated project, serializes create/prune/metadata updates per root, and uses checked atomic metadata writes (`state-file.ts:writeJsonChecked`, preserving unrelated existing stores' write behavior). The native session file stays in its harness's own store and is not cloned into a backing db.

**Model catalog.** The start screen's model and thinking chips ask `/api/harnesses/:id/models?workspaceId=` before any chat exists, and an answer costs a harness spawn (Pi ~4.5 s, OpenCode or omp ~3 s). `model-catalog.ts` keeps one answer per harness and project in `${stateDir}/model-catalog.json`, serves it at once whatever its age, and starts one refresh behind it once it is a minute old; the first look at a project also fills in the other available harnesses' answers there, one spawn at a time. A restart does not wait on a spawn either: after `listen`, `warmSaved` refreshes the saved answers that have gone stale for the three projects asked about last, using the available harnesses only, and fills in the first workspace root's project when nothing is saved yet. Nothing blocks the server's start, and a harness that fails is noted once rather than per project; the route still serves the last answer.

**Status versus transcript.** `/api/overview/events` holds only arrivals that are useful offscreen: chat native id, title, live status and pending question, and room summary. Its replay is bounded at 500 lightweight items and never includes harness text or tool output. The browser opens one refcounted connection through `stream.ts` on the first `useSessions`/`useRooms` mount and closes when both are gone; stale snapshot marker events trigger fallback `/api/sessions` and `/api/rooms` reads (while harness files remain source of truth). Board `RoomManager.subscribe` reuses the room's event log to derive summaries: it never rebuilds native harness streams or mutates their states from a projection.

**Interactive terminal versus harness.** PTYs do not share an agent run's lifetime. They stop once the final viewer disconnects or on server shutdown, have 1 MiB replay, and retain natural exit for 60 s. xterm's necessary DOM-inline layout belongs only in `/terminal-shell.html`, whose source/script is awui's own code. The main web bundle never broadens `style-src 'self'` to accommodate it; agent HTML owns a distinct opaque iframe sandbox independent of this trusted shell. Source/Node calls use a maintained native node-pty backed provider (`@lydell/node-pty`); the Bun executable uses its built-in `Bun.Terminal` to avoid external native-module loading in its virtual filesystem. `terminal-backend.ts` implements one `ProjectPty` interface: write, dimensions, output, exit/pid and kill, never shell command evaluation. A detached viewer kills the live child; it does not leave a hidden terminal process running. Bun.Terminal is POSIX-only here and the Windows binary reports that specific provider limitation without weakening harness access or silently substituting pipes.

**Native artifacts.** Previewing an agent's saved page uses an authenticated headless Chromium request bound to that render id. Its memory-only document has blocked cookies/service workers, fixed origin, and all other requests aborted. Screenshots are real PNG bytes through the bounded in-memory image store and console is captioned, with no arbitrary URL renderer.
**Resume without waiting.** Opening an old Pi, omp, Claude Code, Codex, Grok, or DeepSeek Harness session shows its transcript straight from the session file (`readTranscript`, a few milliseconds) and starts the harness behind it; the status reads *Starting* until it is up, usually under a second. Meanwhile the model picker lists the saved catalog's models for that harness and folder (`ModelCatalog.peek`; the harness's own list replaces it once up, and a folder with none saved yet gets the first started chat's list kept for the next resume), its chips fade in and out and read *Loading…*, and the no-models banner waits for the harness instead of flashing. A prompt or model change made meanwhile goes through once it is. If the harness starts working on its own as it comes up (an extension picking a task back up, as Pi's background-tasks does when it reconciles a job that died with the last process), the chat shows *Working* with Stop, not *Idle*, and a warning above the work says nothing was sent from here. Hermes keeps its history behind its gateway, so its sessions open when the gateway is ready (a session the gateway will not mount still shows its transcript from `state.db`); OpenCode's are read through its server. Session listings are warmed at startup, and Hermes's are served from cache while they refresh.

**Single writer.** `chatId → live session` and `harnessId + native session id → chatId` mean the same session is never opened twice in this process. For omp that also means never two child processes. A second tab or device attaches to the existing chat as another SSE subscriber. **Another terminal or process running `pi`/`omp`/`hermes` is not locked out.** Avoid driving the same session from a terminal while it is open here.

**Run lifecycle.** A run is not marked complete at a message end or a bare `agent_end`. Pi's `agent_settled` and omp's `session_settled`/`prompt_result.sessionSettled` decide it. Sends return `202` once the harness accepts them; output streams over SSE.

**Runs outlive the browser.** A run belongs to the server, not to a tab: close the browser mid-run and it carries on, and any device that opens the chat later (another browser, your phone over LAN or Tailscale) attaches to the same live chat and picks up from the snapshot. A chat waiting on an approval waits for an answer from any device. Only a chat that is idle, has no viewers, and has been quiet for 30 minutes is closed, and its session file stays, so opening it again resumes it. The reaper asks the chat first: one waiting on an answer, holding steps its chain has not run, or due to continue after a usage limit stays open, since a closed chat loses all three.

**Hibernation (config.yml's `hibernate_after_minutes`).** With it set, the same reaper parks a chat earlier: one that has been idle, unviewed (no stream attached), and carrying no deferred work — pending answers, chain steps, background jobs, subagents still out — for that long has its harness child disposed. The native session id is the lease and the mark's key (session-marks.json records `parked`), so the reopen goes through `manager.resume` exactly as any other reopen: the transcript is read straight from the session file (`adapter.readTranscript`), the conversation is present read-only while the harness starts behind it (`DeferredLiveChat`), the same native session is reopened, and the claim in the manager guarantees one live writer — a second writer for one session file never appears, and a reopen racing the park waits on the opening in flight. Only adapters that can read the transcript back park; a chat whose history lives only behind its process is never parked, since reopening it would come up empty. Parked is a mark, not a status: the row shows a quiet square, the chat is out of the live lists, and opening it clears the mark.

**A run does not survive a restart.** The harness's child dies with the process, so the server records the sessions that were running as it shuts down (`resume-intents.json`, bounded to 50, stale after a day) and the first time one of them is opened again sends it one prompt, "Resume working." It never starts a harness on its own: a restart that fired model calls for chats nobody opened would spend money on a screen nobody is looking at.

**SSE.** `GET /api/chats/:id/events` sends a snapshot on connect, then monotonic event ids. It replays from `Last-Event-ID` or `?lastEventId=` when still in the 5000-event window, and resnapshots otherwise. A heartbeat goes out every 20 s, the stream is gzipped (flushed per event) only when the page asks with `?z=1` and the client accepts it, and token deltas are coalesced every 30 ms. Tool output is bounded (head and tail of 16 KB). The client reconnects with jittered backoff (0.5 s→10 s, then stays at the cap), pauses while offline, retries immediately on `online` or when the tab becomes visible, and treats 45 s without a heartbeat as dead.

## The adapter registry: adding a harness

A harness is one adapter file plus a registry entry; the web UI, atui, and the Tern client need no code for it, since they draw what its adapter declares (name, colour, capabilities, setup command). The only per-harness tables are atui's optional mark and spinner. [docs/harnesses.md](harnesses.md) is the full guide: which existing adapter to copy for the agent's transport, the `HarnessAdapter` / `LiveChat` contract, what each capability turns on, every file a new harness touches (registry, config, docs, a scripted fake CLI and its tests), and how to check it against the real CLI. In short:

1. Implement `HarnessAdapter` and `LiveChat` from `src/server/harness/types.ts` in `src/server/harness/<name>.ts`. Normalize everything into `HarnessEvent`. Never pass SDK or wire types further out.
2. Declare `capabilities` honestly. The UI hides or disables whatever is not declared.
3. Register it: a line in `factories` (`registry.ts`), the default `AWUI_HARNESSES` list (`config.ts`), and its `harnesses.<id>` launch settings and `<ID>_BIN` (`user-config.ts`).
4. Test it against a scripted stand-in that speaks the CLI's recorded wire (`tests/fixtures/fake-<name>.mjs`), then against the real CLI (`npm run smoke`).

`HarnessId` is a branded string, so adding one never edits the protocol types.

### Later harnesses via ACP

The natural generic adapter is the [Agent Client Protocol](https://agentclientprotocol.com) (DeepSeek Harness `dsh --profile acp`, `omp acp`, and the Claude Code, Codex, and Gemini ACP bridges). The mapping onto this app's events:

| ACP | This app |
|---|---|
| `agent_message_chunk` | `assistant_delta` (text) |
| `agent_thought_chunk` | `assistant_delta` (thinking) |
| `tool_call` / `tool_call_update` | `tool_start` / `tool_update` / `tool_end` |
| `plan`, `usage_update` | notices / the context chip |
| `session/request_permission` | `request` (InteractionRequest) |
| `session/load` replay | `history()` |
| `session/list` | `listSessions()` / `listRecentSessions()` |
| `session/cancel` | `abort()` |
| session config options | model / thinking / mode |

ACP has no standard steer or follow-up, so an ACP adapter declares `supportsSteer: false` and `supportsFollowUp: false`. Pi and omp do **not** use ACP here. omp's ACP mode cancels a running turn when a new prompt arrives instead of steering, and Pi has only third-party bridges.

**Grok Build** is one adapter here: [`src/server/harness/grok.ts`](../src/server/harness/grok.ts) drives one `grok agent --no-leader stdio` child per chat, and [`grok-transcript.ts`](../src/server/harness/grok-transcript.ts) folds its `session/update` payloads for both the live child and its `updates.jsonl`.

**DeepSeek Harness** is the other: [`src/server/harness/dsh.ts`](../src/server/harness/dsh.ts) drives one `dsh --profile acp` child per chat. DSH's ACP surface deliberately replays no history, and its session files are concatenated zstd frames rather than JSONL, so [`dsh-transcript.ts`](../src/server/harness/dsh-transcript.ts) both finds the frame boundaries and rebuilds the conversation, listing, and usage from `session.v4.jsonl.zstd`. See [DeepSeek Harness](#deepseek-harness) below.

## Pi

Each live chat runs the **installed** `pi` as `pi --mode rpc --session-dir <dir> [--session <id>]` (JSON lines over stdio), so a `pi update` reaches the web UI at once and no pinned SDK can drift from the CLI that wrote your sessions. Pi itself loads its global and project settings, AGENTS files, skills, prompt templates, extensions, and custom models. Extension dialogs arrive as `extension_ui_request`: `select`, `confirm`, `input`, and `editor` become dialog cards, `notify` becomes a notice, and status lines and widgets become chips. The child is up once it answers a `get_state` probe (rpc mode prints nothing unprompted).

- **Sessions:** listing and fork read Pi's `.jsonl` files directly (header, `session_info` name, the active branch by `parentId`), caching each file's summary while its size and mtime are unchanged.
- **Context ring:** the total and window come from `get_session_stats` (`contextUsage`); the system prompt / tool definitions / messages split is estimated from `get_messages` the way pi-ai estimates tokens. Pi answers null tokens right after a compaction (no response has measured the new context yet), and the total then stays unknown until one does rather than taking that estimate.

**Trust.** Pi decides, as its CLI does outside a terminal: an extension's answer, the stored decision in Pi's trust store, then your `defaultProjectTrust` setting, and otherwise the folder is not trusted. Rpc mode never prompts; run `pi` in a folder once to answer the question there.

Tools are Pi's normal active set (your `defaultTools` plus extension tools); this host never narrows them. Model and thinking changes go through `set_model` and `set_thinking_level`, which change only the session, so the web UI never rewrites your Pi defaults.

## omp

omp's npm package requires Bun and ships raw `.ts`, so it cannot be imported into this Node server. Each live chat therefore runs the **installed** `omp` in `--mode rpc-ui`, one child process per chat. `rpc-ui` is the mode with tool-approval and extension-UI requests over the protocol; plain `rpc` has no UI, so approvals would fail closed.

- **Listing:** omp's RPC has no session listing, so a short-lived `omp acp` process answers `session/list` (with a `cwd` for one project, without one for the sidebar's newest sessions across projects) and exits after 60 s idle. `session/list` carries only omp's stored title, which stays empty when omp never generated one; like omp's own picker, the adapter then shows the first prompt, read from the first 64 kB of that session's file (read-only, cached by size).
- **Resume:** `--resume <id>` with `--cwd`. The adapter checks that omp opened exactly that session.
- **Transport:** omp's protocol v1 caps every frame at 1 MiB, so a long session's `get_messages` fails ("RPC response exceeded the transport limit") and big events are trimmed. When omp's ready frame offers protocol v2, the adapter negotiates it and joins the `rpc_chunk` slices (up to 64 MiB a frame). If a history still cannot load, the chat fails with omp's reason and its omp process is closed again.
- **Fallback:** when omp moves a request to its next candidate model (a rate limit, an outage, a rejected tier) it says so, and the chat shows *Switched openai/gpt-5 to anthropic/opus: Rate limited* as a notice while the run goes on.
- **Tools:** omp starts with its normal tool set. The app never passes `--tools`.
- **Home directory:** omp refuses to work in your home directory itself (it would switch to a temp dir), so the UI disables omp for a workspace that is exactly `~`. It never passes `--allow-home`.
- **Lifecycle:** children are killed on dispose and on `SIGINT`/`SIGTERM`. A crash surfaces as a chat error. Protocol types are hand-written from omp 18.4.5 and checked against **18.4.10**: newer minors are assumed additive and stay quiet, while an older build or a different major line shows a warning.

## Hermes

Every Hermes surface — its Ink TUI, the desktop app, the dashboard — runs chats through the one gateway that owns the profile home (`~/.hermes/gateway.lock`), and awui does too: it attaches to that gateway over its canonical WebSocket, starting or recovering one with the CLI's own public verbs when none runs. The stdio `python -m tui_gateway.entry` child remains only as the fallback for a home no gateway can run against — Hermes retired that entry point as a product surface in 2026.9.24, and it refuses to start beside a live owner (exit 1: *refused: … is owned by a running gateway*), which is why a Hermes update broke per-chat children overnight.

- **Attaching, and the dialect shim:** awui follows upstream's public client contract (Hermes's *Gateway Internals*, "Local control socket") rather than reading the home. It finds the owner's control socket — `gateway.sock` when it is a socket only this user can reach, else the `gateway.sock.path` pointer a gateway under a private temp root leaves, and a named profile's root when the profile has none — asks it for its verdict and endpoint (`resolve-profile`, or `identify` on a Hermes older than that verb, 0.23 and earlier), mints a short-lived single-use session ticket (the public form, with `restart_wait: refuse`, retried without that key on an owner that predates it, and checked against the profile and instance it echoes back), and dials the `/api/ws` URL the owner names with the subprotocols it names. That socket speaks Hermes's canonical session wire, where the session verbs differ from the stdio dialect (`session.create` takes a closed contract negotiated via `runtime.describe`; submissions carry a client-minted `input_id` and answer with an admission receipt; edits are revision-fenced `session.mutate` operations; interrupts carry the `execution_generation`; approvals and clarifies arrive as `approval.request`/`clarify.request` events answered with `approval.respond`/`clarify.respond`). `hermes-canonical.ts` translates between the two, the way upstream's own clients do, so a future wire change lands in one shim — negotiated, not guessed — instead of breaking every call site. Nothing is written to the home, and the session belongs to the gateway: it outlives awui, and the TUI, Telegram, and the dashboard see it like any other.
- **What attaching serves:** everything — session rows (`projects.tree`), models (`model.options`), and chats — each over one socket per chat or short-lived probe, no Python child to start. A chat runs beside a live owner (the point of the gateway), and a home nobody owns gets one on demand. When the home's control socket is not something this process can use — Windows' named pipe (whose SID only Python checks), a home whose rendezvous is not the documented shape, an owner that refuses the ticket verb — awui takes the CLI's own public attach step instead (`hermes gateway attach --json [--recover]`, Hermes 0.23.0+1278 and later, the same command its TUI and desktop run): one JSON line with the owner's URL, the subprotocols, a single-use ticket and its endpoint, dialled as given. The same command starts or recovers the owner when none serves the home, so an older CLI gets `hermes gateway ensure` and the socket path and nothing else changes. Discovery reads the owner's own verdict, so an owner that says it is *starting* is waited out (bounded) instead of reported broken, and one that cannot be attached to says why in its words; a gateway that outlived `hermes update` is flagged in its warning line (it keeps serving the code it booted until `hermes gateway restart`).

- **Environment (the stdio fallback):** its gateway child runs under the `hermes` launcher's own environment, which on Nix is `HERMES_PYTHON`, `HERMES_BUNDLED_PLUGINS`/`SKILLS`/`LOCALES`, `HERMES_INSTALL_ROOT`, and a `PYTHONPATH` with plugin dependencies such as mnemosyne. This server is not started by the launcher, so the fallback replays the launcher's setup once (everything before its final `exec`, under the launcher's own shell) and starts the child with the result. An explicit `HERMES_PYTHON` is used while that interpreter can import `tui_gateway`. A launcher with no readable Python — upstream's installer writes a shell script whose `exec` carries an inline `-I -c` bootstrap, and it also exports the bare tool Python as `HERMES_PYTHON` — is asked for its own launch command instead (`hermes --print-runtime-command --module tui_gateway.entry`, the installer's machine boundary), so the child gets the bootstrap that puts the checkout on `sys.path`. Only a launcher that answers neither falls back to `python3` on `PATH`. The attached path needs none of it: `hermes gateway ensure` runs the launcher itself.
- **Sessions:** `session.create` / `session.resume`, and closing a chat detaches its subscription — the session belongs to the gateway and other surfaces may hold it too. Listing comes from `projects.tree` rows over a short-lived probe. Opening a chat creates its session there and then, so it is in Hermes's history — and in the TUI's and the dashboard's lists — before anything is sent. A session the gateway refuses to mount (older awui chats, stored as source `webui`, which `session.resume` answers `not_found`) still shows its transcript, read from `state.db`; a new turn has to start in the Hermes TUI or as a new chat.
- **Runs:** `prompt.submit` (images via `image.attach_bytes`), streamed as `message.*`, `reasoning.delta`, and `tool.*` events; `session.interrupt` stops. Opening a chat asks the session to stream its reasoning (`config.set` `show_reasoning`), as the CLI and the ACP editor do: the gateway leaves that flag off until a viewer sets it, and the flag is the session's, not a config write. **Steer** is `session.steer`: Hermes puts the text into the running turn's next tool result, with no new user turn and no interruption (on the canonical wire it carries the execution generation, and Hermes refuses a stale one). When nothing live can take it (the turn ended first, or the message holds an image or a `/` command), the text is queued as the next prompt instead. **Follow-up** is a `queued` submit, which waits for the turn to end and is never turned into a live correction, whatever the profile's `display.busy_input_mode` says. Edit/Retry cuts the session at the chosen turn (`truncate_before_row_id` on the stdio wire, a `rewind` mutation before the new prompt on the canonical one).
- **Decisions:** approvals and clarifies — server requests on the stdio wire, `approval.request`/`clarify.request` events on the canonical one — become approval and dialog cards, answered with the wire's own response. Prompts this UI cannot serve (sudo, secrets, vault, previews) are declined with a notice.
- **Config:** model and reasoning are session edits (`config.set` on the stdio wire, fenced `session.mutate` operations on the canonical one) on Hermes's full effort ladder (`none` … `max`, then `ultra`, as Hermes Desktop offers it); when the route sends a lower level than the one picked (no provider takes `ultra`, so most send `max`), the thinking pill and picker say so (`Ultra → Max`), from the session info's `reasoning_effort_wire`; rename, compact, todos, usage, and context come from the gateway. Its context gauge (`context_used`/`context_max`/`context_percent`) rides every usage payload — `session.usage`, `session.info`, and the turn's `message.complete` — and the turn-ending one arrives after the settle, so the adapter keeps the gauge from whichever payload named one last instead of reading `session.info` alone, which left the ring a turn behind. Hermes publishes no per-model effort levels, so its models carry no level chip.

- **MoA:** Hermes's Mixture of Agents presets appear in the model picker as its virtual provider (*Mixture of Agents*, one entry per preset), so a chat can run on one for the whole session. `/moa <prompt>` runs one prompt through the default preset and restores the previous model, saying so in the turn. Each reference model's advice opens as its own Markdown fold under the model's label, while the fan-out (`2/2 references done`) and the aggregator handoff read on the status line. The presets themselves (reference models, aggregator) are configured with `hermes moa configure`.
## Claude Code

Each live chat runs the **installed** `claude` as `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --permission-prompt-tool stdio`, one child per chat: the stdio protocol Anthropic's Agent SDK drives, without the SDK's pinned copy of the CLI. Your login, settings, hooks, MCP servers, skills, memory files, and permission rules apply as in the terminal.

- **Sessions:** a new chat gets its id up front (`--session-id`); resume is `--resume <id>`. Listing, history, and fork read `~/.claude/projects/<cwd with every symbol as ->/<id>.jsonl` (`CLAUDE_CONFIG_DIR` moves it): the active branch by `parentUuid`, cut at the last compaction, titled by your rename, then Claude's own title, then the first prompt. Messages sent mid-turn (stored as `queued_command` attachments) count as prompts, as they do on screen. A fork writes a new file cut after the chosen prompt. Copy resume command gives `claude --resume <id>` from the project folder: the session's file is the CLI's own, so a terminal picks it up where awui left it (the picker's filter is on the entrypoint the file records, `sdk-cli`, not on the file).
- **Runs:** each model call streams as partial messages; tool calls show after the call that made them, and subagent (`Task`) internals stay inside their tool. **Steer** sends with `priority: "next"`, landing right after the running tool call; **follow-up** waits in the CLI's queue for the next turn. The echoed (replayed) message marks when either starts. **Stop** cancels anything still queued (`cancel_async_message`) and interrupts.
- **Decisions:** `can_use_tool` requests become approval cards: *Allow once*, *Allow for this session* (the CLI's suggested rules, scoped to the session, never written to your settings files), or *Deny*. `AskUserQuestion` becomes one card per question. Other host callbacks (hooks, MCP, elicitation) are declined.
- **Config:** the handshake's models with their effort levels; the thinking picker offers the chosen model's (none on a model without them) and shows the effort it really runs at (`get_settings`' `applied.effort`, the model's default when no settings file names one). Model via `set_model`, effort via `apply_flag_settings` (this session only, and only a level the model lists: the CLI takes any word there), thinking shown as summaries. The permission mode starts as the handshake's `current_permission_mode`, changes with `set_permission_mode` at any time, and follows the `permissionMode` on the CLI's `status` frames (its own changes, such as leaving plan mode); Auto is offered only on a model the handshake marks `supportsAutoMode`. Context comes from `get_context_usage` (Claude Code's own categories, minus deferred tools and free space); usage is summed per turn, and a resumed session starts from its file's per-message usage and the CLI's last cost snapshot. Each call's usage also names which prompt cache it wrote (`cache_creation.ephemeral_5m_input_tokens`/`ephemeral_1h_input_tokens`), so the chat carries `promptCacheTtlMs` and when that cache runs out (`promptCacheExpiresAt`, counted from the request) on its usage. Rename is `rename_session`; compact sends `/compact`; todos come from `TodoWrite`.
- **Trust:** print mode skips Claude Code's workspace-trust dialog, so only folders under `WORKSPACE_ROOTS` are offered. The handshake's account details (email, plan) stay on the server.
- **Tools:** every child runs with `ENABLE_TOOL_SEARCH=true`, so Claude Code defers MCP tool schemas and the model loads the one it needs through `ToolSearch` instead of receiving awui's two servers' schemas in full on every turn. A value you set yourself (in your environment, `config.yml`, or Claude's own settings `env`) is left as it is; `ToolSearch` is in `--allowedTools` beside awui's tools, so loading one never stops at an approval card.

## Codex

Each live chat runs the **installed** `codex` as `codex app-server`, one child per chat: the JSON-RPC dialect (`{id, method, params}` lines over stdio) that Codex's own TUI, IDE extension, and desktop app drive, not the non-interactive `codex exec`. Your login, `~/.codex/config.toml` (model, providers, MCP servers, hooks), and sandbox policy apply. Codex's app-server defaults a new thread to a read-only sandbox, which is not a coding agent, so awui starts one in its **Auto** mode; the permission pill switches between the three modes above.

- **Sessions:** Codex writes a rollout per thread, `~/.codex/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl` (`CODEX_HOME` moves it). Listing, forks, and resume go through the app-server's own `thread/list`, `thread/fork`, and `thread/resume`; awui never writes a rollout. Resume without waiting reads the file (`readTranscript`), and Usage across chats sums its `token_count` lines.
- **Runs:** a send is `turn/start`; the prompt, thinking, and answer stream as items (`item/started`, `item/agentMessage/delta`, `item/reasoning/summaryTextDelta`, `item/completed`), and a shell or patch call is a row with its output and diff. The run is settled only by `turn/completed`; **Stop** is `turn/interrupt`. **Steer** is `turn/steer` with the running turn's id (Codex refuses a stale one). **Follow-up** is Codex's own queue (`thread/queue/add`), which runs the message as the next turn and can be listed, removed, and replaced, so the queue the status stack shows and edits is Codex's.
- **Decisions:** a command or patch approval (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`) is a card in Codex's own words with *Allow once*, *Allow for this session*, and *Deny*, answered with a decision Codex offered. A `request_user_input` question is one card per question. Requests awui cannot serve (extra sandbox permissions, MCP elicitation, a ChatGPT token refresh) are declined with their reason; the current time is answered, as the harness asks.
- **Config:** `model/list` gives the models and each one's effort levels; model and effort ride on the turn and follow the thread. A config that names a model the account cannot run (a paid model on a free ChatGPT plan, say) would fail every turn with Codex's *modelNotFound*, so a new or resumed chat starts on the catalog's own default instead and the pill names it. The context ring is the last call's tokens against the model's window, and `thread/tokenUsage/updated` carries the session totals. Rename is `thread/name/set`; compact is `thread/compact/start`; fork is `thread/fork` at the chosen turn. Codex publishes no todo list or slash commands over this protocol, and awui writes no rollout, so there is no handoff or in-place rewind (history could be cut, but the files would stay as they are).
- **Limits:** the Usage panel reads `account/rateLimits/read` from a short-lived app-server (at most every three minutes) and follows `account/rateLimits/updated` while a chat runs.
- **Render:** when awui has a render endpoint and token for the chat, the child is started with awui's `render_html` MCP server in `-c mcp_servers.awui…` overrides (your own MCP servers still load), and the page lands in the chat like any other harness's render call.

## OpenCode

OpenCode 2 is driven through its own HTTP API: awui starts **one** private `opencode serve` (on a free loopback port, with a password awui picks and hands over in `OPENCODE_SERVER_PASSWORD`, so nothing secret passes through its output) the first time a listing, a preview, or a chat needs it, and every OpenCode chat shares it, as OpenCode's server is built to hold many sessions. With no chat open it stops after ten minutes. Your providers and their keys, agents, plugins, permissions, and sessions are OpenCode's own; its model entries carry provider settings, which awui never passes on.

- **Sessions:** listed per project by OpenCode's `location`, newest first (child sessions left out); a new chat's session is made on its first message, so an untouched chat leaves nothing behind. History, previews, search, and usage read the session's messages through the API, a page at a time (at most 5,000). Fork is OpenCode's `fork` before the next prompt.
- **Runs:** one event stream (`/api/event`) is read and handed to each chat by session. Thinking and text stream per step; a step's tool calls fold under the words before them, an edit as the diff OpenCode reports. A prompt goes in with no delivery, **steer** with `steer` (it lands at the next step), **follow-up** with `queue`; OpenCode's inbox is the queue awui shows and edits. **Stop** is `interrupt`, which also drops what was queued. Edit and Retry stage and commit a revert to before the prompt (the conversation only), then send.
- **Subagents:** a delegation (`task`, or oh-my-opencode-slim's `subagent`) runs a child session, which the call names as soon as it starts; awui follows that session's events, so the card shows the agent's model, tool calls, tokens, cost, and time as it works, and its answer after. *Open transcript* reads the child session (only a child of the chat's own session). A `background` run goes on reporting after its call returns. Reopened, each run is filled in from its child session's totals. Child sessions stay out of the session list.
- **Decisions:** a permission request is an approval card (*Allow once*, *Always allow* with the pattern OpenCode would save, *Deny*); a form (the question tool's) is one card per field, its answers sent back together. A request answered in OpenCode's own client closes here.
- **Config:** the project's models (OpenCode's list), each model's variants as its thinking levels (`none` and `default` are not levels); a change goes to `POST /session/{id}/model`, or waits for the session before the first message. Context is the last step's tokens against the model's window; usage and cost are OpenCode's own totals.
- **awui's own tools:** OpenCode has no extension API, so `render_html` and the orchestration tools reach a chat as two MCP servers registered on that shared server when the chat opens — `awui-r-<id>` and `awui-o-<id>`, each a `local` entry running awui's bridge under Node with the chat's own two variables, and `codemode: false` so they stay tools rather than entries inside Code Mode's `execute`. Nothing is read from or written to your OpenCode config; your own MCP servers keep loading. The id is a hash of the chat's tokens (never the token: a server name becomes part of every tool name sent to the model), and OpenCode exposes a tool as `<server>_<tool>`, so a render call arrives as `awui-r-<id>_render_html` and its page marker is lifted onto the card. Chats in one project share that server and so one MCP set, so each chat's session also gets permission rules — deny `awui-*`, then allow its own two, last match wins — which is what keeps one chat's tool token out of another chat's hands. The pair is re-applied before a turn when anything landed after it (OpenCode appends a broad allow on an "always" answer, and the last match wins), and a session no chat opened — a child session from OpenCode's task tool, or one another client made — is given its parent chat's pair, else the bare deny, since a session with no rule allows every tool. Registration is repeated before each turn (a restarted server has no runtime set), removed when the chat closes, and a refusal costs only the tools: the chat runs without them and the server logs the reason once, without a token.

## Grok

Each live chat runs the **installed** `grok` as `grok agent --no-leader stdio`, one child per chat, speaking the [Agent Client Protocol](#later-harnesses-via-acp) as JSON-RPC 2.0 lines over stdio. awui never attaches to the shared `grok` agent leader (`--no-leader`), never passes `--always-approve` or `--leader`, and leaves the permission mode to Grok's own config. Your login and `~/.grok` settings apply, inherited from the environment; the server sets only `GROK_DISABLE_AUTOUPDATER=1` on each child, and `GROK_HOME` (else `~/.grok`) names the agent dir.

- **Sessions:** a new chat is `session/new` and resume is `session/load`; Grok writes its own store. Listing, history, and usage read `~/.grok/sessions/<encoded cwd>/<id>/` (`summary.json` and `updates.jsonl`) read-only — a group directory whose `.cwd` file names the project is included too, when the encoded name does not fit in one file name — and awui never writes inside `~/.grok`.
- **Runs:** a send returns once `session/prompt` is written. Grok does not echo the user prompt, so that row is awui's. The call then streams `agent_message_chunk` (text) and `agent_thought_chunk` (thinking), tool calls fold from `tool_call`/`tool_call_update` (a result's diff block becomes the chat's diff), and `turn_completed` records the turn's tokens and cost. A run is settled only when the `prompt` RPC result arrives, with its `stopReason`; **Stop** sends `session/cancel`.
- **Subagents:** `spawn_subagent` uses the same delegation card as the other harnesses. `subagent_spawned` and `subagent_finished` fill the rows (a retry is another row on that call; a background child stays running after the tool returns), with the child's status, model, tokens, and answer. Opening a row reads that child's own `updates.jsonl`, and only a child this chat spawned.
- **Decisions:** `session/request_permission` becomes a card whose options are Grok's own words, answered with the option's own id or cancelled; Stop and Close cancel a pending one on the wire.
- **Config:** the handshake's `modelState` and `configOptions` give the models, their effort levels, and the current selection; a change goes through `session/set_config_option` (a bare value string), and a level the target model does not list is refused before anything is sent. Context is the last turn's prompt size against the model's window. Grok's `inputTokens` already include cache hits, so those are not added again; a `usage_update` from the CLI, when one arrives, replaces that figure with the window it names. Usage sums the per-turn tokens and cost. Todo and command listings are empty, as ACP has neither.
- **awui's own tools:** when the chat was given its tokens, `session/new` and `session/load` carry awui's two MCP servers as stdio entries beside the user's own — `awui` (`extensions/render-html-mcp.mjs`) and `awui-orchestrate` (`extensions/orchestrate-mcp.mjs`), each run by a real Node with the chat's own two variables. Nothing is written to `~/.grok`, and no plugin or config file is touched. Grok names an MCP tool `<server>__<tool>` and may route the call through its `use_tool` dispatcher; the fold renames awui's own servers' calls to `mcp__<server>__<tool>`, the spelling the render card and the orchestration tools read, and a render result's `awui-html-render:` line becomes the page. Without a Node to run them, or without that family's token, the tool is simply not offered.

## DeepSeek Harness

Each live chat runs the **installed** `dsh` as `dsh --profile acp`, one child per chat, speaking the [Agent Client Protocol](#later-harnesses-via-acp) as JSON-RPC 2.0 lines over stdio. `DSH_HOME` (else `~/.dsh`) names the harness home; awui passes the user's own environment, so DSH's login, models, settings, and permissions apply. awui never passes a flag that loosens DSH's sandbox or approval policy.

- **The ACP profile is an optional bundle.** DSH ships the `acp` profile template but not its app bundle in every installation (the Nix package carries only the web and headless bundles). awui's setup hint names the pinned command: `dsh plugin --profile acp add @deepseek-ai/dsh-acp-app@<dsh version>`. `dsh plugin` runs DSH's own pnpm into `~/.dsh/profiles/acp`, so the profile survives a Nix rebuild and needs no global install. A missing bundle shows the harness as unavailable with that command as the reason, never as a failed chat.
- **Resume needs the session's providers.** DSH refuses to resume a session whose recorded model route has no registered adapter. The shipped ACP profile mounts the base providers; if your web profile configured others (`llm-pi-ai`'s `providers:` block, for example), copy those patch rows into `~/.dsh/profiles/acp/cordis.patch.yml` too. Otherwise awui lists a web-created session but resuming it fails with DSH's own *no adapter registered for provider …* reason. A session created through awui's ACP profile resumes there, and the web UI can resume it after the same rows are in its profile.
- **Sessions:** a new chat is `session/new` and resume is `session/resume` (DSH has no `session/load`). Listing, resume-without-waiting, and usage read `~/.dsh/sessions/<project key>/<session id>/session.v4.jsonl.zstd` read-only: one zstd frame per DSH append, so the adapter walks the frame headers without decompressing whole blocks, and a torn final append loses only its own batch. Titles come from `session/title` (the LLM's title or DSH's first-prompt fallback), else the first prompt. A subagent session is left out, and the log's own `cwd` must match the project.
- **Live text:** DSH's stock ACP bridge sends only committed messages, a model step at a time. awui streams them as they are written with its own Cordis plugin, [`extensions/acp-flow.mjs`](../extensions/acp-flow.mjs), loaded per chat by a `--patch` overlay in awui's state folder (`dsh/acp-flow.patch.yml`). The overlay turns off the profile's `acp` row and inserts the plugin with that row's inject list and config, read from `dsh --profile acp --dump-config`. The plugin runs the same installed bridge inside it on a message stream it owns, and adds DSH's own provider deltas (`agent/assistant-stream`) as a `_acp-flow/assistant_stream` extension notification, only for the sessions it opened (never a subagent's). Nothing is installed or changed in the profile, and the bridge's own updates go out unchanged. The committed chunks then repeat what streamed: they replace the bubble only when DSH kept something else (a cancel keeps a safe prefix), and a failed attempt's text stays, marked, with the retry in a new bubble. A profile whose `acp` row is not the stock bridge, or holds a `!!js` expression, keeps the stock bridge; so does every chat after the plugin once fails to load (DSH's boot report is caught, rather than waiting out the handshake). `AWUI_DSH_FLOW=0` turns it off.
- **Runs:** a send writes `session/prompt`; text and thinking arrive live (above), or with the stock bridge as whole committed blocks (`agent_message_chunk`/`agent_thought_chunk`). Tools fold from `tool_call`/`tool_call_update`; an edit's live diff comes from its arguments, and a resumed one from the result's `meta.diffs`. `usage_update` is the context chip's occupancy, and token totals come from the committed messages (DSH prices nothing on this surface, so cost stays unpriced). The run settles only when the `prompt` RPC result arrives; **Stop** sends `session/cancel`. ACP has no steer, follow-up, fork, rename, compact, rewind, or queue edit, so those stay off.
- **Decisions:** `session/request_permission` becomes a card with DSH's own *Allow once*/*Reject* options, answered with the option's id or cancelled. The request carries only the call id, so the card's title and arguments come from the earlier tool call; an approval with no known call still shows the options.
- **Config:** the session's config options give the model catalog (DSH's opaque `["provider","model"]` values, shown as `provider/model` keys), the route's reasoning levels, and the current selection. A change goes through `session/set_config_option`; DSH's empty reasoning value is shown as `default`. The catalog is per session over ACP — there is no session-less model call — so a brand-new workspace's start screen shows no picker until its first chat opens; that chat's own config has the catalog. **Refresh models** re-selects the current route, which asks DSH for the catalog again without changing it.
- **Render:** when awui has an endpoint and token for the chat, the config declares awui's `render_html` MCP server on the ACP session (stdio, Node, the chat's own env), so DSH calls it as `mcp__awui__render_html` and the page lands in the chat like any other harness's render call. Without a Node to run the server, or without a token, the tool is simply not offered.
- **Nix:** the flake's `dsh` package ships the web and headless apps, not the ACP one; the profile install above is the only extra step, and it lives in your home, not the store. A profile bundle left older than a newer `dsh` (after a flake update) is reported as a warning, with the reinstall command, instead of failing a chat.

## Any ACP agent (config-defined)

`config.yml`'s `harnesses.acp` entries become harnesses without an adapter file each: the registry builds one `AcpAdapter` (`src/server/harness/acp.ts`) per entry, under the entry's own id, on the same transport (`acp-client.ts`) and update fold (`acp-updates.ts`) that the generic path shares with Grok's and DSH's own adapters. Nothing about the agent is written anywhere: awui runs its command in the chat's project folder with the user's environment plus the entry's own variables.

- **Capabilities come from the agent.** `initialize` (run on discovery and again per chat, never with a model call) says whether a session can be resumed, whether prompts may carry images, whether it takes MCP servers over HTTP, and which auth methods it offers; the session's `configOptions` say whether it lists models and reasoning levels, so the model pills appear from the first chat that saw them. ACP has no steer, follow-up, rename, compact, or rewind, so those are declared false, and awui adds no routes for them.
- **Sessions.** A new chat is `session/new`; a resume is `session/load` when the agent advertises `loadSession` (the replayed `session/update` stream becomes the chat's history) or `session/resume` when it advertises only that (the chat continues with no visible transcript, because nothing is replayed). An agent advertising neither refuses the resume with its reason. awui lists no sessions for these agents: ACP v1 has no session list, and awui does not read the agent's own store.
- **Runs.** A send writes `session/prompt`; text and thought chunks stream, tool calls fold from `tool_call`/`tool_call_update` (a `diff` content block becomes the chat's diff, `locations` become the row's paths), a `plan` shows as a notice, `usage_update` feeds the context ring (occupancy only; no per-turn token split is invented), `session_info_update` names the chat, `available_commands_update` fills the `/` menu, and `config_option_update` re-reads the pills. The run settles when the `prompt` RPC result arrives; **Stop** sends `session/cancel`. An update kind the client does not know is noted once per chat.
- **Approvals.** `session/request_permission` is a card whose options are the agent's own names, answered with its own `optionId` or cancelled; the request carries only the call id, so the title and arguments come from the earlier tool call.
- **awui's own tools.** The session mounts awui's `render_html` MCP server as a stdio entry when a Node can run it, and the orchestration tools over HTTP when the agent advertises `mcpCapabilities.http`, else as the stdio bridge — the same two families Grok and DSH get, per chat, never written to the agent's config.
- **Bounded and quiet.** A child that dies mid-run settles the run as failed with its stderr tail; unknown updates and unknown requests never crash the chat (an unimplemented method is answered with `-32601`, so the agent is never left waiting).

## Approvals and extension dialogs

Every harness keeps its own approval protocol (omp's `tools.approvalMode`, Pi/omp extension dialogs, Claude Code `can_use_tool`, Codex `requestApproval`, OpenCode permissions/forms, and Grok/DSH `session/request_permission`). The adapter translates them to one `InteractionRequest` without inventing grants. Pi and omp can also present `select`, `confirm`, `input`, and `editor` dialogs in this shared shape:

- It takes over the composer and stays in the conversation as a card that records the outcome.
- Pending requests are part of the SSE snapshot, so they survive reconnects and show on every attached device. The **first answer wins**; a later answer gets `409`.
- Stop and Close cancel pending requests through the harness's cancel path.
