# Using awui

The web UI, region by region. The terminal clients are in [In a terminal](terminal.md).

- **Sidebar.** New chat comes first, then the harness row. New chat never creates a chat: it shows the main pane's **start screen** (see *New chat*) with the folder picker open over it, so it works before any folder is chosen; the harness row under it filters the session list to one harness and picks the agent for new chats (its hover text and menu say so). Below them sit session search and the sessions. The sidebar focuses the current folder (Hermes Desktop's one-folder view): its name and count on top (its **+** starts a chat there, the row's ⌄ switches to another project without leaving the view), a **‹** button beside its name to go back to every folder (the list slides in the direction you went; reduced motion just changes it), then that folder's sessions of the selected harness, most recent first in date groups. *All projects* shows every folder, grouped by project and ordered like Hermes Desktop: sessions by their last activity (their last turn, else when they began; only opening one does not move it), projects by their newest session, and a git repository's projects together (the one you are in, then the one on `main`/`master`, then the other branches and worktrees, each naming its branch). Inside a project, the run of what you did last has no heading (cut at a real pause of half an hour or more, about five sessions down); below it come calendar headings (Yesterday, Earlier this week, Last week, Earlier this month, then months, with the week starting on your locale's day), never one above the first row, and *Show N more in …*. Drag a session (or **Move up** / **Move down** in its menu, or **Alt+↑/↓**) to a new place inside its heading; the order is kept per project and harness for every device (`$XDG_STATE_HOME/awui/session-order.json`), and a session that sees new activity still goes back to the top. Under the search box, **Running**, **Needs you**, and **Today** chips (one on at a time, each with its count; Running and Needs you appear only while something matches) narrow the list to the chats working now, the ones waiting on an answer or an approval, or the ones with activity since midnight; they combine with the text search, the choice is remembered per device, an empty result offers **Clear filter**, and Escape in the search box clears the text, then the filter. **Filters**, at the end of that row, hides whole kinds of session instead, each counted so an empty list is never a mystery: **Sleeping** (nothing running, nothing waiting, and no activity for a day), **On the default branch** (a chat in the project's own checkout on `main`/`master`, not in a worktree), **Started by a routine** (a session a scheduled prompt opened; the server marks it in `session-marks.json`), and **Started by an agent** (a delegated child, whose place in the orchestration records says so). The chat on screen is never hidden, so it can still be closed from the list; **Show everything** clears the toggles, and the choice is kept per device. Search covers all projects and the selected harness's sessions; a dot on each row marks its harness (the harness menu, which scopes the list and picks the harness for new chats, is the legend), and a spinning ring marks a session that is working. Clicking a session in another project switches to that project, and a project row's **+** switches the folder to that project and shows the start screen for it. Each folder carries a badge — its monogram (its first letter, in a hue taken from its name) until you set an icon for it (one or two characters) from the folder's menu on this device. Only folders inside `WORKSPACE_ROOTS` that the harness can open are listed. A green dot means the session is already open in this server; clicking it attaches to that chat rather than opening a second writer. A row's **⋯** (or a right-click, or a long press on a phone) **pins** it to a *Pinned* list at the top or **archives** it out of the list; *Show N archived* at the bottom brings archived ones back in place, and a search finds both. The same menu marks a session **unread** (an accent dot beside its title until it is opened here, kept by the server like every other mark) or **Select sessions** starts a selection: click rows to pick them, Shift extends the run from the anchor, Escape leaves, and the bar over the list settles, archives, pins, or snoozes an hour for all of them (one toast, one undo) or **settles** it (done for now: it leaves the list until a run starts in it again) or **snoozes** it for an hour, until tomorrow at 9:00, until next Monday, until a time you pick, or until the account's limit resets (it comes back then, or as soon as it fails or asks for something); *N snoozed* and *N settled* at the bottom bring them back in place, and every one of these changes shows a toast with **Undo** (or **Ctrl+Z** outside a text field). Resting the mouse on a row (T3 Code's hover card) shows its last prompt and the start of the answer, the model, how many turns, and the files it changed, read without opening the session; when nobody typed it, the card also says how it began (a routine or another agent) and, when it is quiet, that it is sleeping. Above the projects (T3 Code's inbox), **Needs you** lists chats waiting on an answer or an approval and **Working** (folded by default) the chats that are running; the chat on screen stays where it is. Marks are kept by the server in `$XDG_STATE_HOME/awui/session-marks.json`, so every device sees them; the harness's session files are not touched. The gear left of the collapse button opens **Settings** (see *Settings*). Drag the sidebar's right edge to resize it (200–560 px, remembered per device). The panel button at its top right folds it away, and the chat header gets one to bring it back. Narrower than 1200 px (a vertical monitor, a tiled half screen) it folds away by itself and returns when the window widens (`autocollapse_sidebar`); reopened by hand it stays open until the width crosses back, and one you collapsed yourself stays collapsed at any width. The handle also takes arrow keys (Shift for bigger steps) and Home/End, and double-clicking resets it.
- **Settings** (the gear left of the collapse button, or the palette). Two panes in one dialog. The rail on the left lists the sections — This device, Appearance, Layout, Agents, ACP agents, Desktop app, Network and sign-in, Folders and access, and the Awui harness's providers — with a search field above them: typing narrows the list and the open section's rows alike (`port` keeps Network and sign-in and its Port row; a section's own name keeps all of it; a word that matches nothing says so), and Escape empties the search rather than closing the dialog. Every section stays mounted while another is shown, so an edit made in one survives switching away and the one **Save** in the bar under both panes writes them all; a section holding a field a save would be refused for carries a dot in the rail. That bar holds the form's state, **Discard**, **Save**, the restart notice (whichever section is open) and the version, and the dialog keeps one height: only the section scrolls. ↑/↓, Home and End move through the rail, the section last opened is remembered per device, and `?settings=<section>` (e.g. `?settings=network`) opens Settings on that section. On a phone the rail is the list and a section opens with **Sections** to go back, the Save bar under both; nothing scrolls sideways.
- **Tabs** (Hermes Desktop's). The chats open in this browser sit in a strip above the conversation, each in its harness's colour with its title; a working ring marks one that is running, and a dot one that finished while another was shown. Clicking a session in the sidebar shows it in the current tab, or switches to its tab when it is already open; **Ctrl/⌘-click**, **middle-click**, or **Open in new tab** in the row's ⋯ menu (or right-click) opens it in a new tab, as does **+**, which puts a tab on its own with the start screen — the first prompt fills that tab. A session shows the moment it is clicked: its tab, title, and harness come up at once over a loading screen (a ghost of the thread in the harness's colour) that fades when the conversation has drawn. The fetch starts early (on hover for a chat the server holds, on the mouse press for one it resumes), and a long chat draws its last few turns first and fills in the older ones above them, out of sight. Closing a tab (its ✕, middle-click, or Delete) only hides it: a run keeps going on the server. ←/→, Home/End, and Enter move through the strip; the browser keeps Ctrl+T/W/Tab. **Drag a tab sideways** to reorder the strip (a few pixels of slack keep a click a click; the others slide aside), or press **Alt+Shift+←/→** on the focused tab. **Pin tab** in a tab's right-click menu (or the palette) moves it to the left, narrow, with just its harness dot and a short title: a pinned tab has no ✕ and is not closed by middle-click or Delete until you unpin it, and a drag or key move never carries a tab across the line between the pinned and the rest. **Ctrl+[** and **Ctrl+]** go back and forward through the chats you have shown, **Alt+Shift+T** reopens the last closed tab (the browser keeps Ctrl+Shift+T), and **Ctrl+Alt+Enter** in the composer sends, then opens a new chat in a new tab. Tabs, their order, and their pins are remembered per device: after a reload, or a server restart, each one reattaches to its chat or resumes its session when you open it. On a phone the strip gives way to an *Open tabs* list at the top of the drawer.
- **Harness menu.** One row under *New chat* shows the current harness and its version, short and comparable (`1.0.2`, `2026.9.24`: a build that reports a placeholder `0.0.0`, as Hermes on Nix does, shows its release date instead), with the CLI's full version line on hover; its menu lists every harness (Pi, omp, Hermes, Claude Code, OpenCode, and whatever else is registered), each in its own colour, and keeps an unavailable one listed, greyed, with the reason. Arrow keys, Enter, and Escape work. Picking one scopes the sidebar to that harness's own sessions and picks the harness for new and resumed chats; open chats stay on the harness that created them. A harness's colour is a theme token it declares (`accent`), or the first one free, so a new adapter needs no CSS. The composer's harness chip uses the same menu to hand a chat off, and the start screen's agent chip uses it to pick the agent for the chat to come.
- **Project.** The start screen's folder chip picks the folder: its menu lists the recent folders (newest first), then *Choose another folder…* for the browser — which walks `WORKSPACE_ROOTS` one level at a time, or takes a typed path. With no folder chosen the chip stands out and Enter in the box opens the browser, keeping whatever was typed.
- **New chat.** With no chat on screen, the main pane is a start screen: one question ("What should {agent} do in {folder}?"), a text box, and the agent, model, and folder chips under it. The model chip picks the model the new chat starts on (the harness's own default until you pick one); it appears once a folder is chosen, because a harness lists its models per project. The server keeps each harness's answer per project (`$XDG_STATE_HOME/awui/model-catalog.json`) and shows it at once, after a restart too, asking the harness again behind it once it is a minute old; the first look at a folder also fills in the other harnesses' lists there, one at a time, so switching the agent chip does not wait on a spawn. The model menu's Refresh asks the harness now. Images go in the box as in a chat's composer (paste, drop, or the image button) and are sent with the first message. Typing a message and pressing Enter creates the chat and sends it — nothing starts until then. With no folder chosen, Enter opens the folder picker and keeps the draft; pressing Enter again sends. The Awui harness asks anything and has no folder chip. *New chat* everywhere (the sidebar, the tab strip's +, the palette, a project's +, the installed app's shortcut) shows the start screen, keeping any open chats' tabs; the sidebar's *New chat* also opens the folder picker over it (Escape keeps the current folder, and a picked one puts the cursor in the box).
- **Each turn** shows:
  - your prompt as a bubble;
  - under it, faint (45%) until the turn is hovered or has focus, and full on the latest turn (Claude's chat; always full on touch screens and under reduced motion, and a long press on the message opens them as a sheet): when it was sent (the clock time, "Mon 3:41 pm" within a week, "Oct 12, 3:41 pm" before that, the full date on hover), **Retry**, **Edit**, **Copy**, and **Copy prompt link** (see *Prompt links* below). Retry runs the prompt again, with its images; Edit opens it in place (Ctrl/⌘+Enter sends, Esc cancels) and, when the turn has a file checkpoint, can undo its file changes first. Hermes, Pi, omp, and OpenCode replace the message in the same session; OpenCode reverts the session to before it (its own revert, the conversation only: the files stay as they are, for the checkpoint to undo) and then sends. Hermes does it as Hermes Desktop does (`prompt.submit` cutting at the message's stored row, which Hermes soft-archives rather than deletes). Pi and omp can only do it from an extension (their RPC `fork` and `branch` start a new session), so the server starts them with [`extensions/rewind-to.ts`](../extensions/rewind-to.ts) (`-e`): Edit and Retry run `/rewind-to <n>`, check the session went back, then send the prompt; what followed stays in the session as a side branch (`/tree` reaches it), and the command is kept out of the composer's "/" menu. In a terminal, `/rewind-to` alone picks the prompt from a list. Claude Code keeps a session's past as it is, so there both run in a branch from before the message, on the same model, thinking level, and permission mode: a fork, or a fresh chat for the first message; the original chat stays in the sidebar.
  - one **tool card** folding the agent's thinking, tool calls, and approvals (open while running, collapsed after: a turn from history opens nothing, and a failed call is marked by its tint and the **N failed** tally rather than by a card left open). Its header is the **"Worked for 12s · Used 6 tools"** line with a stack of icons for the kinds of tool used while the card is closed, since an open card's rows carry their own glyphs (an MCP server is a kind of its own, drawn as a monogram), the turn's `+42 −7`, and, when a call failed, a **"1 failed"** button that opens the card and goes to the first failed row. Each call is a row of icon, sentence, facts, and a status mark in one column (a spinner, a check that draws itself when the call settles in view, or a red mark); a failed row is tinted and keeps its reason on the sentence's line, muted (the line that says why, not the command's banner), with a ↻ **Ask to retry** mark at the row's end (finger-sized on a phone), its words on hover. A settled card of one call is just that row, with no header saying it again. An opened call is one tile: its sentence and its body share one surface, the sentence keeps its verb, facts, and mark (*Ran · 5 passed ✓*), and the body says the rest once: the whole command, the file's link and a read's line range, or the address, then the diff, terminal, or file, with *Full output* at its foot when there is more than the tile shows. A failed call's reason steps aside while it is open, since its output says it in full. A command that starts by changing into the project reads without that `cd … &&`. Cards, opened calls, and thoughts grow open and shrink shut (the rows below glide rather than jump); a card or a call unfurls on a spring, its edge uncovering the body and running a little past it before it settles, more for a tall output than a short one. A call that starts while you watch grows into its card. On the latest turn a failed row also has **Ask to retry**: awui never runs a harness's tools itself, so it sends the agent a message naming the call and its error ("Retry the failed tool call (running npm run e2e). It failed with: …") as the next prompt, or queues it as a follow-up while the agent works where the harness takes them, and disabled where it does not. On a phone the facts sit under the sentence. While a run goes, the header names what it is doing instead of "Working": *Thinking*, then the running call's own sentence (*Running npm test*), then *Writing* once the answer streams (real states only, never a timer; a change waits 600 ms behind the last so a burst of fast calls does not flicker, and the label is a polite live region), and settles on *Worked for 12s*. At the header's right end, in the rows' status column (so its icons line up with the rows' icons, and nothing moves as the run settles), an eight-ray spinner (rays that fade one after another) shows the run is going (left blank while the open card's running row, or a waiting approval, spins just below it), and when it settles in view the spinner gives way to a check that draws itself (on a phone, a settled card with a failure tally leaves the check out, since *Worked for …* already says it settled and the label needs the room); the label glides to each new phase's width. All of it is off under reduced motion. What the agent writes to you between tool calls is a reply, shown as one and in order, not folded away: *reply, run a command, then answer* reads as the reply, the command's fold ("1 command"), and the answer, the same while it runs and after. Only the stretches of work fold, and a stretch that is only thinking shows its thought row: a thought reads itself out while it streams, then folds back to its first line once the agent moves on. A stretch above a reply folds away by itself as the reply lands (the one still running stays open), and a card shuts on a spring, with a few pixels of give as it lands. Work the agent does after writing its answer (a todo update, a rendered page, a memory note) keeps its place below the reply, as its own fold, instead of jumping into the fold above it. A call whose result carried a picture — a `read` of a screenshot — shows it in the open row as the same numbered thumbnails a prompt's images get, growing into the same full-size viewer; the picture's bytes never reach the page, only `/api/images/<id>`. That store keeps the newest pictures within a budget and empties on a restart, so a thumbnail whose bytes are gone by the time you look is left out rather than shown broken. Each tool call reads as a sentence (*Reading src/app.ts* while it runs, *Read src/app.ts · 412 lines* after, *Couldn't run npm test* when it fails; `tool-sentence.ts`), with a count only where the call's own result holds one (a shell call whose harness reported an exit code shows `exit N`), so a call it cannot read shows just its time. Where an output is a shape the app is sure of, its summary is read instead of counted (`tool-facts.ts`): a Vitest, Jest, pytest, cargo, or go test run (*25 passed · 1 failed*, and which test), tsc and eslint (*3 errors in 2 files*), rg and grep (*4 results in 2 files*), `git status` and `git diff --stat`, npm, pnpm, and pip installs, and a JSON array (*12 items*); an output no parser is sure of is never guessed at. A command whose output was a test run wears a flask icon instead of the terminal's, in its row and in the header's stack. Every call stays in the card, however long the run. A tool call that runs past 1.5 s shows its time after its line, counting while it runs and kept once it is done; a call with output has **Full output** under it, opening all the server kept (16 KB) in a sheet that follows the call while it streams, with Copy, and a call whose result never comes (a cancelled question) stops when the run does and says it got no result; **`tool_style: lines`** (Settings → Tool calls) draws the same folds flat — no card surface, no icon stack, the header naming what the run ran ("Worked for 11s · 4 commands"), and each call's facts right after its words rather than pushed to the edge — the list older versions had, with the collapse, the springs, the failed tally, and an opened call's output unchanged.
  - an **answered request** (Approve, Deny, a chosen option) does not just vanish: its card fades and blurs while its height glides down to one quiet line above the composer, "Approved: Allow tool: read", with a check or a cross that draws itself; the line leaves by itself, and the request row in the turn keeps the record. Reduced motion shows the line at once;
  - a **queued message** (a follow-up or steer waiting above the composer) glides from its row into the prompt it becomes when the agent takes it, and the prompt lights up softly as it lands; the status stack grows to its content instead of appearing at full height. Reduced motion skips the glide and the light;
  - a **plan** the agent handed over for review (Claude Code's `ExitPlanMode`, [pi-plan-mode](https://www.npmjs.com/package/@narumitw/pi-plan-mode)'s `plan_mode_complete`) as a card (T3 Code's): the plan as Markdown, its first lines until *Show the whole plan*. On the latest turn, with the agent idle and nothing asked, **Implement** sends "Implement the plan." and **Revise** starts a message about it; while the harness itself asks about the plan (Claude's approval, pi-plan-mode's review menu), its question above the composer is the way to answer;
  - **Code blocks** have a slim header with the language ("TypeScript", "bash"), **Wrap** (wrap long lines or scroll them sideways, one choice per device) and Copy on hover. An unlabeled block has no header band: its Wrap and Copy float over its top corner on hover (a touch screen, where they always show, keeps the header). In a finished answer a block of a language the file viewer knows is coloured, and one of six lines or more has line numbers (never selected or copied); a block past 2000 lines or 100 KB stays plain, and a streaming answer's blocks stay plain until it settles. A one-line shell block (`bash`, `sh`, `zsh`, `fish`, `console`) in a finished answer also has **Run**, which runs it in the chat's project folder with that shell (60 s limit, output kept to 100 kB) and shows the exit code and output under it, with Copy and *Add to message*. Any signed-in device can do this, as it can already ask the agent to; the server logs that a command ran, not the command.
  - the answer as plain text with a Copy button (every copy button, in code blocks, the file viewer, output sheets, and the pair dialog too, is one component: the icon blurs into a check and its name turns to "Copied", "Link copied", or "Turn copied" for a moment, announced politely, "Copy failed" when refused; the row under an answer is faint like the prompt's, and Retry's arrow turns once on a press); on hover (or keyboard focus) its row also says how the turn went, "24s · first token 1.2s" (the turn's time, and the wait for the model's first words), each part only when the harness reported what it needs; the per-turn token rate is left out because no harness reports output tokens per message (the session's average is in the context ring). A phone shows it in the long-press sheet's title and always on the row; **Timing** (a clock button beside Copy, and in the phone's sheet) opens the turn as a waterfall: every thought, reply, tool call, and subagent as a bar on a time axis from the prompt to the settle (ticks at round values), the slowest call marked, a subagent call's runs folded under it, each row named for a screen reader ("Ran npm test, 0.4 s to 38.2 s, slowest call") and moved through with the arrow keys; tokens and cost appear only on subagent runs, the one place the harness reports them, and a turn with no times says so; **Copy turn as Markdown** (beside Copy, and in the phone's sheet) puts the whole turn on the clipboard for an issue or a PR: `## Prompt`, `## Work` (a line per tool call, like `- **Edit** \`src/app.ts\` (+12 −3)` or `- **Run** \`npm test\` (failed)`, with the agent's replies between them), and `## Answer`; no diffs, tool output, or thinking, and cut at 200 KB (Export as Markdown in the chat menu keeps the diffs);
  - **Code blocks** have Copy on hover; a one-line shell block (`bash`, `sh`, `zsh`, `fish`, `console`) in a finished answer also has **Run**, which runs it in the chat's project folder with that shell (60 s limit, output kept to 100 kB) and shows the exit code and output under it, with Copy and *Add to message*. Any signed-in device can do this, as it can already ask the agent to; the server logs that a command ran, not the command.
  - **Quote**: select text in an answer and a Quote button appears above it; it adds the passage to your message as a Markdown quote (`> …`), and sent prompts show quotes as a quote block;
  - **Fork from here** on a finished answer: the session is copied through that turn into a new chat and opens in its place. Pi, omp, and Claude Code each get a new session file cut to the same branch, Codex forks its thread at that turn (`thread/fork`), and OpenCode copies the session with its own fork. Not offered for Hermes, which has no fork, or for a command the harness answered itself (it stores no turn).
  - **Handoff** from the harness chip in the composer: the chat continues in another harness as a new session holding the transcript — the first prompt and the last 10 turns verbatim, a one-line-per-turn summary of the middle, tool calls as plain records (never replayed), images noted but not carried — and a draft in the composer runs there as the first new turn. A busy chat is stopped first; the source is left as it was. Pi and omp receive a **copy**: the turns are written into their own session store. Hermes, Claude Code, and OpenCode cannot store a past conversation (Hermes records a turn only by running it; Claude Code's session files are not written by hand here; OpenCode's sessions live in its own database), so they receive a **briefing** instead: a fresh chat whose first prompt is the record above, framed as context that nothing in it should run again, ending on your draft (or asking for a two- or three-line status from the record alone). It costs one model call; its budget is 40,000 characters, giving up tool output first, then folding the oldest turns into one line each. The menu says which a target gets, and the banner after says how many turns the summary covered. A briefed harness has read about the earlier work rather than done it: "re-run that" starts afresh.
  - a **Changed N files** list for edits and writes, with the lines they added and removed (`+42 −7 · 3 files`, in the diff's green and red). The same `+42 −7` stands beside the turn's *Worked for …* line, so it reads with the fold closed, and follows a running turn as edits land. The counts are the edits' own, taken before a long diff is cut for display; a `+` after a number (`+42+`) says an edit reported no count, so the sum is at least that.
  - **Undo file changes** (↶ on a finished answer) when the project is in a git repository: before each prompt the server snapshots the work tree, so a turn's files can be put back as they were before its prompt — whatever changed them since, the agent's edits or its commands. A preview lists each file (put back, deleted because it is new, or brought back) with a tick to leave any out, and can also fork the chat from before that turn; its Undo button is held for a moment (a ~600 ms press fills it, or hold Enter or Space), so a stray click puts nothing back; the banner afterwards has *Put back* to undo the undo. The conversation itself is not changed, and the agent is not told. Snapshots go into a shadow repository in `$XDG_STATE_HOME/awui/checkpoints/` that borrows the project's objects: the project's own `.git` is only read, and `.gitignore`d files are never captured or touched. Each session's checkpoints are kept there too, so a resumed session still has them; a prompt the harness rewrites (a Pi prompt template) gets none.
  - **File timeline** (the chat's ⋯ menu, or the palette, once a checkpoint exists): the files before each prompt and as they are now, on one rail of points (`#1`, `#2`, … `Now`, each with its prompt and when). Pick two and every file that changed between them shows, added, deleted, or changed, with its lines; a path opens the file viewer. From a prompt's point, *Undo to before #N…* opens the restore dialog for it. At most 60 files are listed with their lines (the rest are counted), each bounded as a tool's diff.
- **Project-new tabs.** The sidebar project **+** opens a fresh draft tab in its folder, leaving your active conversation in its previous tab with its draft and ongoing run. Return to the draft at any time to start its chat, rather than losing the other tab.
- **Review** (the chat header's *Review N* button, or the palette): every file the agent edited or wrote in this chat, with each edit's diff in order under its turn. Click (or Enter on) any line to start a comment thread on it; a line that already has one opens that thread, where you reply, **Resolve** it, or delete it. A resolved thread stays, struck through with a tick, until you delete it (an *All* chip in the footer shows them beside the open ones), and anything left open rides in the next batch. Comments live on the server, so every device sees the same review and it survives the tab or the chat being closed. A comment pins to the line's text as well as its number: when the agent edits the file again it follows the line to its new place, and when the text is gone it stays where it was, marked *line changed since*. *Send N comments* asks where the batch of open threads goes — this chat, a new chat in this project (choosing its harness), or another chat of the project (resumed first if it is not open here) — and one prompt lists them numbered, each under its `file:line` and code, with resolved ones counted and left out. While the target is working they queue as a follow-up where the harness has one, and the option says to wait where it does not. Nothing is cleared after a send: each thread says when it last went, and the next batch carries whatever is still open. At most 200 threads a chat, 50 notes each (older resolved threads are pruned first), and this device's older per-browser comments become threads the first time the panel opens. Each line the agent wrote carries a small dot in the gutter, and each file's header says how many of its lines came from this chat; the rule is that a line is the agent's when a tool call's own diff added it (or an earlier call added that text and the line has not changed since). A line the agent wrote that the file no longer has — the agent's own later rewrite, one of its commands, or an editor — gets an amber ring instead, with the honest limit in its hover text: the transcript cannot tell an editor's change from one of the agent's commands. Files the panel could not read (gitignored build output, a file too big for the bounded read) keep no marks, and neither does the transcript's inline diff: it would need the whole chat re-indexed on every streaming event.
- **Model switches.** A thin divider ("Switched to GPT-5.5") sits before the turn whose answer came from a different model than the turn before, read from the model each answer records, so it shows on reopened sessions too (Hermes's stored transcripts name no model, so older Hermes turns have none).
- **Inside the fold.** Each step is a single quiet line (`read · src/app.ts`); click it for the input/output panel. Red appears only for real failures.
- **Subagents.** A delegation — omp's `task`, [pi-subagents](https://github.com/nicobailon/pi-subagents)' `subagent`, Claude Code's `Task`, OpenCode's `task` and [oh-my-opencode-slim](https://github.com/alvinunreal/oh-my-opencode-slim)'s `subagent` — lists its agents, one row each: status, agent type, brief, and tool, token, time and cost counts. Seen working it opens by itself and shows what each agent is doing; a row opens to the brief and the agent's answer, and **Open transcript** slides in that agent's own conversation (read from the file its harness wrote, or OpenCode's child session, refreshed while it runs). A session omp copied keeps its delegations but not their transcripts, so those are found in the session it was copied from. omp's background agents turn done when their results come back, whether delivered, waited for, or killed. Agents an omp `eval` cell spawns (`agent()` in its Python, one cell or several) are that call's rows too, written `Parallel · 2 agents` or `Chain` and read from the cell's own status events, with each agent's answer from its `yield`; the eval call is still a code run, so its card wears the agents chip and opens as they start.
- **Delegated tasks.** When an agent delegates through awui's orchestration surface (`delegate_task`, see [orchestration.md](orchestration.md)), the parent chat's status stack lists the task: a chip for how it stands (*Working*, *Waiting*, then *Done*, *Failed*, or *Cancelled*), its title, the agent running it (harness · model · role), how long it has run, and Open and Cancel. The row opens to the child's last line, or to the question it is waiting on. **Open** shows the child chat beside this one (its own tab on a phone, where there is no second pane); **Cancel** stops it and everything it started, and asks once first. The rows are the server's own records, kept current by the chat's stream rather than polled, so a reloaded page and a reopened parent still list their tasks. A delegated child is an ordinary chat with a *Delegated by …* chip in its header, which opens the chat that started it. A chat whose agent sets a status line (`set_status`: working, blocked, ready for review, or done, plus one sentence) shows it in the sidebar's row, the chat header's sub row, and the hover card, with when it was set on hover, so you can read where a long run stands without opening it.
- **Agent-rendered pages.** In a Pi, omp, Awui, Claude Code, Codex, or OpenCode chat the agent has a `render_html` tool (registered by [`extensions/render-html.ts`](../extensions/render-html.ts), which the server loads with `-e` as it does the rewind extension): it hands one self-contained HTML document — a chart, table, diagram, mockup — with inline `<style>` and `<script>`, and the page appears full-width above that turn's answer. It shows in a sandboxed iframe with an opaque origin (`sandbox="allow-scripts allow-forms"`, never `allow-same-origin`), so its scripts cannot reach the app's session or storage. The server stores the document in `$XDG_STATE_HOME/awui/html-render/` with a small bootstrap in its head that hands it the active theme as CSS custom properties (`--bg`, `--text`, `--accent`, …) before its own scripts run, reports its content height so the frame fits without an inner scroll, and opens its links in a new tab. Pages load only for the chat that produced them (`/api/chats/<id>/html-render/<renderId>`). atui cannot render a page in a terminal, so a render call's row names the page instead ("Render · Fake report · 160px, page in web UI"). Claude Code gets the same tool from awui's own MCP server ([`extensions/render-html-mcp.mjs`](../extensions/render-html-mcp.mjs), no dependencies): each chat's CLI is started with `--mcp-config` naming it (your own MCP servers still load) and `--allowedTools mcp__awui__render_html`, so it runs without a prompt; Codex gets it through the same server in its own `-c mcp_servers.awui…` overrides; it posts to the same endpoint with the chat's token, and since an MCP result carries only text, the page's reference rides on its last line, which awui takes off and attaches to the card (only for that tool, live and in history). A compiled awui binary starts it with the `node` on `PATH`, which Claude Code itself needs. OpenCode gets both tools the same way but without touching any file: awui registers the two servers on OpenCode's own shared server for each chat (`awui-r-…` for a page, `awui-o-…` for delegation), takes them off when the chat closes, and scopes the chat's session so another chat in the same project cannot call them with its token. Hermes still has no `render_html`: its gateway adds MCP servers only to the profile's config file, which awui does not write.

While a compaction runs the conversation row shimmers, and when it ends the panel says "Compacted ✓" for two seconds as the numbers roll down. (The bar stands in for the ring here: the ring is a single 16 px pie, the used share filled in.)

While the window is unknown only the figure shows.

At most 200, each up to 20,000 characters, names unique.

The steps run one after another, each when the run before it settles on its own, even with every browser closed; a handoff moves the rest of the chain to the new chat. ## The headless CLI

`awui run` drives the server that is already running, so a script, a cron job, or an editor hook can use the agents without a browser:

```bash
answer=$(awui run --wait "Run the tests and fix what fails")   # stdout is the answer; the chat id goes to stderr
id=$(awui run --project ~/code/app "Add a test for parseEndpoint")
awui send "$id" "Now do the same for parseCommand"
awui wait "$id" --timeout 120
awui chats --json
```

`--harness <id>` picks the agent (else the server's first available one, the web-only Awui chat surface last), `--project <path>` the project (else the current folder), and `--model <id>` the model. It is a thin client of the same JSON API the browser and atui use: it finds the server the way the desktop shell does (`$AWUI_URL`, else the port in `<state folder>/server.json`, else `127.0.0.1:4783`), needs no sign-in on this machine, never starts a server, and writes nothing to the state folder. The run is the server's, so it keeps going when the command exits.

Without `--wait`, `run` prints the chat id and returns as soon as the harness accepted the prompt. With `--wait` it waits until the run settles (an hour at most) and prints the answer on stdout, with the chat id on stderr so `answer=$(awui run --wait "…")` takes the answer alone; `--json` prints one object instead, `{"chatId", "status", "answer", "error"?, "usage"?}`. `send` adds a prompt to a chat that is open there and returns once it was accepted; `wait` waits for that chat and prints its answer. `chats` lists the chats open on the server — one tab-separated line each (`chatId`, status, harness, title), or `--json` — and nothing that is only a session file on disk, since nothing can be sent to it without opening it first.

Exit codes: **0** the run settled, **1** it failed or the server refused (the reason on stderr), **2** the command line was wrong, **3** the run had not settled when `--wait` or `wait` gave up — the run itself still goes on. `awui run --help` lists the flags.

## The Awui harness

**The Awui harness** is a chat surface in the harness dropdown, web UI only (atui omits it). For reading, asking, and computing, never editing the project: it is a `pi` child with pi's four writing/executing tools denied (`--exclude-tools bash,edit,write,powershell`), so a chat there can read, search the web, and use read-only MCP servers, but cannot edit files or run shell commands. Two awui extensions give it the chat-surface extras: `render_html` publishes a page (a chart, table, or mockup) into the thread — it writes only to awui's own render store, never the workspace — and [`eval_python`](../extensions/eval-python.ts) runs a short snippet in a throwaway tmp dir (stateless, timeout-capped, output-bounded), so it can compute without touching the project. It keeps its own agent directory and per-project sessions under awui's state folder — never the user's `~/.pi/agent` — and declares no fork/rewind capability. Its sidebar shows a flat, dated chat history (Pinned, Today, Yesterday, each day this week, Older), Claude.ai-style, instead of projects; the project tree belongs to the coding harnesses. `Settings → Awui harness` edits the providers it can call (name, base URL, API kind, key — stored only in its own `models.json`, the key never shown back); the `litellm` provider is seeded from `~/.pi/agent/models.json` the first time and never overwritten after that.

**Share Pi's login** (the checkbox in the same section) opts into more: the harness's `auth.json` becomes a symlink to your `~/.pi/agent/auth.json` — one login for both sides, a `/login` or token refresh in either reaching the other — and every provider from your `~/.pi/agent/models.json` is copied in once, when you turn it on; after that the list is the harness's own to edit. Off by default, and the link is the only thing that ever crosses between the two agent dirs.
