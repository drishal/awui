# Security

What the server does to keep a local app local, and how to expose it to other devices on purpose.

- Binds `127.0.0.1` by default, or `0.0.0.0` with `HOST=0.0.0.0`. No CORS. `Host` must be loopback, in `ALLOWED_HOSTS`, or (with `HOST=0.0.0.0`) one of this machine's own LAN addresses or hostname. `Origin` must match `Host`, and `Sec-Fetch-Site: cross-site` is refused. These failures return `403`, which also blocks DNS rebinding and cross-site requests against the open local mode.
- **This machine needs no sign-in.** A request counts as local only when the TCP peer is loopback, the Host is loopback, and no proxy headers (`X-Forwarded-*`, `Forwarded`, `Tailscale-User-*`) are present. So a LAN client faking `Host: 127.0.0.1`, or Tailscale Serve proxying over loopback, is never local. The trade-off: any process or user on this machine can drive the agent through the UI. That is the same reach they already have by running `pi`/`omp`/`hermes` as you.
- **Other devices sign in** with `auth.username`/`auth.password` from `config.yml`, or the login from `npm run set-password`:
  - `set-password` stores only a salted scrypt hash, mode 0600. `auth.password` is plaintext in `config.yml` (forced to mode 0600) and is hashed in memory with a salt derived from the cookie secret, so restarts keep devices signed in.
  - Sign-in issues an HMAC-signed cookie bound to that `host:port` and to the credential fingerprint: `HttpOnly`, `SameSite=Strict`, ~30 days, and `Secure` on Serve hosts. Changing the password signs every device out, and signing out voids that device's cookie (copies included) until it would have expired: the signed-out list is kept in `awui/signed-out.json` in the state folder.
  - Five wrong tries lock that address for 15 minutes, and every failure costs 400 ms. Over Tailscale Serve, where every device arrives from loopback, the lock is per tailnet login instead.
  - Without a configured login, every non-local request is refused, and `HOST=0.0.0.0` or `ALLOWED_HOSTS` will not start.
- **LAN access is plain HTTP.** On your home network the password and chats are not encrypted; use Tailscale (HTTPS through Serve, or the encrypted tailnet) when you are away. NixOS's firewall also has to allow the port on the LAN interface (see below). Other devices can read project git status, but changing this machine's git checkout (stage, unstage, commit) always answers `403 local_only`, even for a full password session.
- If `ALLOWED_TAILSCALE_USERS` is set, Serve requests must also carry an allowed `Tailscale-User-Login` (trustworthy only because the backend is behind Serve).
- **Invitations** (Settings → Invitations; `GET`/`POST /api/invites`, `PATCH`/`DELETE /api/invites/:id`) give a sign-in additive grants instead of full access. The vocabulary is fixed and small — `chat.read` (read chats, sessions, files, usage, and the live streams), `chat.write` (send prompts, open, close, resume, and rewind chats, edit the queue, run commands, and the git writes), `chat.approve` (answer an approval card), `settings.manage` (read and change settings, restart, manage the Awui harness's providers and ACP agents), `workspaces.manage` (open workspaces, browse the host's folders, manage worktrees and interactive terminals), `routines.manage` (create, change, run, and delete routines), and `boards.manage` (drive board rooms, their bots, and their queues). There is no role that implies all of them; an invitation lists exactly what it allows, and every protected route declares the one grant it needs and is refused with `403 missing_grant` (which names the grant) when its session's invitation does not include it. Managing invitations is itself a `settings.manage` action, so a limited session cannot widen itself. The invitation lives in `awui/invites.json` in the state folder (mode 0600, checked temp+rename write, at most 200): a name and its grants, nothing secret. A sign-in bound to one (`POST /api/login` with `invite`, or the `?invite=<id>` link the invite UI hands over) carries only the invitation's **id** in its session cookie — never the grants — so the server resolves the allow list on every request: revoking an invitation, or editing its grants, applies to its live sessions at once (a revoked session is refused everywhere with `missing_grant`, never silently full again). A password sign-in that names no invitation is a full session, as every existing account already is; local use on this machine is always full.
- Harness credentials are never read, returned, or logged. Each harness uses its own local auth.

- **Guest links are not logins.** A chat's Share menu (`POST /api/guests/:harnessId/:nativeId` with the chat's `workspaceId`) mints an expiring link (24 h, at most 32 live) whose token exists once in the create response and is stored only as a SHA-256 hash (`awui/guest-sessions.json`, 0600). Redeeming (`POST /api/guests/redeem`) binds **one browser**: a second browser redeeming the same token is `403 guest_in_use`, and the signed guest cookie carries the browser key in the session cookie's invite field. A guest session sees only that chat through `/api/guest`, `/api/guest/history`, and `/api/guest/messages` — title, harness, workspace *name*, expiry, a text-only history (user and assistant text, at most 16 KB an item, last 200; no tool output, args, thinking, request payloads, or paths), and a queue for messages the **owner** releases (`POST /api/guests/:id/messages/:messageId/send`, which resumes the exact native session and sends it; a busy session refuses with `409 busy` and the message stays queued). Revoking (`DELETE /api/guests/:id`) or expiry applies at once (`410 guest_expired`). A guest cookie never becomes a full session: on every route, a bound guest session resolves to its (empty) invitation allow list, so all other `/api` routes refuse it with `403 missing_grant` — on a local server without a password too. Board and side chats cannot be shared.
**Native account pinning.** `GET /api/chats/:id/accounts` narrows provider, 1-based index and current marker to opaque ids. It carries no email addresses, stored credentials, credential file paths, or token values. `POST /api/chats/:id/account` selects only a listed provider/index near current session provider while idle and calls native `/session pin` on this exact attached child; foreign ids or provider model mismatch cause `404 unknown_account` or `409 different_provider` before any auth operation. A missing live implementation produces `unsupported`. This does not change a harness-level current pool, global account preferences or provider file, and does not claim a new-child `--account` flag. Exhausted current account sources block the next queued prompt until this current harness's fresh quota read clears them or a person explicitly continues. Missed or failed quota checks never count as recovery.
- **Run** (`POST /api/chats/:id/run`) executes a one-line shell command from an answer's code block in the chat's project folder, for any signed-in device (the same reach those devices already have through the agent): one line, at most 4000 characters, a 60 s limit after which its whole process group is killed, and 100 KB of output kept. Nothing else runs a shell. Strict CSP (`'self'` only, no inline script or style, no CDNs), `Referrer-Policy: no-referrer`, and `frame-ancestors 'none'`.
- **A repository's own settings run nothing by itself.** A project's `awui.yml` (`GET /api/workspaces/:id/project-config`, `POST /api/workspaces/:id/project-config/trust`, `POST /api/workspaces/:id/worktrees/:treeId/setup`) is untrusted input wherever the repository came from: at most 64 KB, strict keys, and a `shared:` entry that is absolute or holds `..` is refused before anything is applied. Its `setup` command runs only when awui's own state folder records the sha256 of the exact file the person was shown (`$XDG_STATE_HOME/awui/project-config-trust.json`, keyed by the project's real path) *and* the request asks for that run; a hash that no longer matches is `409 config_changed`, a refused file cannot be trusted at all (`422`), and the tree a setup runs in comes from the project's own worktree records, never from a path a client sends. The command is handed to the host's shell as one line, with a five-minute limit, a 32 KB output cap, and the same environment rules every other spawn uses; no path from the file is returned to a browser.
- **A retried mutating request does not run twice.** A client may send `Idempotency-Key` (8–128 letters, digits, or `_ . : -`) on any `POST`/`PUT`/`PATCH`/`DELETE` under `/api`. The first request runs and its status and JSON body are remembered for ten minutes, so a repeat with the same key and body gets that same answer back with `Idempotent-Replay: true` instead of starting a second chat or sending a second prompt. A repeat while the first is still running waits for it (up to 30 s, then `409 request_in_progress`); the same key with another body or on another route is `422 idempotency_key_reused`, and a key of the wrong shape is `400 invalid_idempotency_key`. A client that hangs up does not cancel the work: the key stays running, and the retry gets the answer the route produced (a route that never answers is let go after the same 30 s, so the key runs again). The store is per process and in memory: 1000 answers of at most 64 KB, oldest first, and a restart forgets it all (a 5xx, a stream, an upload, and the orchestration surface are never remembered or replayed). An answer past 64 KB is not kept but its key is spent: the request already ran, so a repeat is `409 idempotency_answer_not_kept` rather than a second run — a real retry sends a new key. Keys are scoped to the session that sent them, so one device's key can neither replay nor block another's.
- **direnv** (`POST /api/workspaces/:id/direnv-allow`): allows a project's `.envrc` by id (the workspace must be open and under the roots). It runs `direnv allow`, writing the user's own consent record, the same file a terminal writes; a remote device can allow one the same way it can ask the agent to reach the project's environment anyway.
- **Upload** (`POST /api/workspaces/:id/upload?name=`): writes one new file into an opened project, the bytes as the raw body (8 MB limit on that route only). The name is reduced to its base (`../x` lands as `x` inside the project), the project's real path is checked first, and an existing file is refused (exclusive create, so nothing is replaced and there is no check-then-write race).
- **Git writes** (`POST /api/chats/:id/git/stage`, `/unstage`, `/commit`): stage or unstage at most 200 files, or commit what is staged, for any signed-in device. A path must be one the project's own `git status` lists — `..`, an absolute path, and any file it does not list are refused — and the message is at most 4000 characters. Commands run through the hardened runner: no hooks, no fsmonitor, no `GIT_*` from the server's environment, so a repository's hooks and config never run by surprise.
- **Harness status** (`GET /api/harnesses/:id/status`): discovery for one harness, asked again when something would otherwise refuse it — a harness can come back after the server started (a Hermes gateway that finished starting, a CLI just installed) — at most once every 5 s, so a broken one is not re-probed per request. The harness menu asks it about the rows it shows as blocked, so they stop being greyed out without a page reload.
- **Health** (`GET /api/health`) needs no session and answers only `{ ok, build, pressure }` — the web bundle's id, and the sampler's one-line view of the server's own machine (state, sample counts, last-toast time). No chats, no paths, no credentials.
- **Opened workspaces are revalidated on every lookup** (`Workspaces.get`, not only on `workspaces/open`). The realpath is checked for existence, directory shape, and presence within the configured roots; a renamed project replaced by a symlink outside them is refused instead of silently becoming a new readable/uploadable root. A realpath race can never be fully eliminated by pathname-based child spawning, but a persistent replacement cannot survive the next request.
- **Managed worktrees** (`GET`/`POST /api/workspaces/:id/worktrees`, `DELETE .../:treeId`) live under the validated project's `.awui/worktrees`. Their `.awui/worktrees.json` metadata is reconstructed one workspace at a time with a per-project lock and persisted using a checked temp+rename write. Tampered metadata naming an outside path is ignored. Prune only removes a managed clean tree: no `--force`, and no implicit clean/delete of content elsewhere. `.awui` is control data, not an agent-readable project file listing. A new tree is seeded from the project's checked-in `.worktreeinclude`, whose paths are confined the way workspaces confines itself: absolute paths and any `..` segment are refused outright, and every source — or any file inside a copied folder — whose realpath leaves the project is skipped, never copied or linked. Symlinked `[link]` entries point at the resolved project path (a relative target), copies are bounded (50 entries, 20 MB, 2000 files, depth 16) and never overwrite an existing tree file, and the create response's report is a bounded payload. A checkout-pr tree (`POST .../worktrees/checkout-pr`, `POST .../:treeId/archive`) takes the PR's number and a task name: the head branch is resolved server-side with `gh pr view` (never a path the client sends), fetched from origin, and the tree's own `awui/pr-…` branch is cut at that commit. Archive runs only when GitHub says the PR is MERGED, the tree is clean (`.awui` aside), and HEAD still sits on the recorded branch — a refusal keeps the worktree and names the problem.
- **Races** (`GET /api/races`, `GET /api/races/:id`, `GET /api/races/:id/members/:chatId/diff?path=`, `POST /api/races/:id/winner`, `POST /api/races/:id/cleanup`) are the comparison a `POST /api/compare` starts. The record lives in `$XDG_STATE_HOME/awui/races.json` (0600, through the checked temp+rename write): at most 50 races of at most 8 members, each keeping the prompt's first 2000 characters and never a path outside its own project (a hand-edited row that names one is dropped on load). A race is pruned only when none of its members' chats is working. Every route revalidates the project through `workspaces.get()` — the file route included, which then resolves the member's tree so one replaced by a symlink out of the project is refused — and the list route reads no git, so the record alone is one cheap call. A member's counts are a bounded `git diff --numstat` (`--no-ext-diff --no-textconv`) against its recorded fork point, cached for five seconds, and cover tracked files only (a new file the agent never added is in neither a count nor an apply); the file route runs `git diff` with `--literal-pathspecs` inside that member's own worktree, refuses anything but a relative path with no `..`, and resolves the realpath so a symlink cannot carry a read out of the tree, then bounds the diff as a tool's (800 lines, 40 KB). `winner` with `mode: "keep"` only records the pick; `mode: "apply"` writes the winner's diff (at most 2 MB, `git apply` without `--3way`, which would stage it) into the project's working tree as an unstaged change, and only when that checkout is clean and its HEAD is still the fork point — otherwise 409 and nothing is written. That patch is generated with options of its own — `--no-ext-diff --no-textconv --no-relative` and explicit `a/`/`b/` prefixes, so a repository's `diff.noprefix` or `diff.relative` cannot scatter a file or a textconv driver rewrite one's bytes — and carried as raw bytes, never decoded to UTF-8, so a Latin-1 or binary file lands exactly as the agent wrote it. It never commits, pushes, checks out, or moves a branch. `cleanup` removes a loser's worktree with a plain `git worktree remove` only when its chat is not running, it has no uncommitted work (`.awui` aside; a `git status` that fails counts as work), its HEAD is still the branch the record names (a detached HEAD or another branch there keeps the tree, since commits only it holds would vanish with the folder), and the commits its tree's HEAD has against the winner's (or the project's) reference are none — or the request listed that member in `discard`, which then allows `git branch -D`; a count git cannot give keeps the tree as an unmerged one does, and a refusal by git keeps the tree or the branch, reported per member. One apply or cleanup runs per project at a time (409 `busy`), so two races in one checkout cannot interleave. A removed member's chat is closed through the chat manager, never by touching a session file.
- **Interactive terminal** (`POST /api/workspaces/:id/terminal`, then its input/resize/events/delete routes): opening a project shell is an explicit authenticated action; it uses the user's own interactive shell in the validated project, not a freeform command API. At most five live PTYs and thirty opens/minute, 10–400 cols, 4–120 rows, 16 KiB input chunks (64 KiB total request), 1 MiB replay, 60 s exit-afterglow. Last browser detach or server shutdown kills the process tree. `terminal-shell.html` only runs awui's xterm code in its own document (needed for DOM inline styles); its separate CSP and source/origin-checked message protocol are not shared with agent HTML. Main app CSP remains `style-src 'self'` and does not become `unsafe-inline`.
- **HTML visual previews** (`POST /api/chats/:id/html-render/:renderId/preview`) authenticate the owning chat before rendering its stored page, never accept a URL or a script/cookie, block all outbound network except a fixed in-memory page, and cap execution, screenshot, and console data. This does not weaken the opaque iframe sandbox for ordinary agent HTML.
- **Agent-page browser actions** (`POST /api/render/action`) allow `snapshot`, `click`, `fill`, `scroll`, `screenshot`, and `close` on charts/pages the calling chat actually published via `render_html`. The required `x-awui-render-token` selects one authorized live chat (no cookie/ambient session fallback, no cross-chat ids, no ownership bypass including close). The driver opens only that chat's saved HTML at the fixed local `preview.awui` origin in a new memory-only Chromium context per page; no arbitrary external URL, arbitrary script evaluation, cookies, storage profiles, or popup sharing. Other requests are aborted and navigation-bearing links are refused before execution. Inputs use bounded IDs/CSS (512 chars) and text (4096 chars), action sequences are serialized per render id, and interpreter metadata is limited to 40 relevant controls plus 16 short console lines. Screenshot tools return image-store references, never stash or reflect arbitrary native transcript data. `browser_action` is an optional tool on each render-enabled bridge, not a general browser or invokable `eval`, and stays unavailable through `x` window controls without that owner's HTML provenance. Open tabs are owner-disposed separately; `close` discards transient DOM, so reopening reads the original saved document rather than a pseudo website re-used context.
- **Orchestration tools** (`GET /api/orchestration/tools`, `POST /api/orchestration/call`, `POST /api/orchestration/mcp`) are mounted before `requireAuth` like `/api/render`: a chat's harness child authenticates with the 32-hex token it was spawned with (`X-Awui-Orch-Token`, or `Authorization: Bearer` on the MCP endpoint, which is what an MCP client sends), never a cookie, so a signed-in device elsewhere can neither mint one nor use one chat's token for another chat's work. The token names one live chat and dies with it (12 h cap, renewed by a chat restart) and is never written to disk. Every call is authorized as that chat and reaches only its own tasks and children; a read-only harness (`awui`) and Board-owned chats get no token at all. Arguments are validated against the tool catalogue's own schema, briefs and follow-ups are capped at 32 000 characters, what a parent reads back is bounded (a page of at most 200 items, each cut to 16 KB, image references dropped), and a delegation can only name an *open* project by id, never a path. A status line an agent sets (`set_status`) is one word and at most 200 characters of its own text, collapsed to one line and kept for the newest 500 sessions in `$XDG_STATE_HOME/awui/agent-status.json`; it carries no transcript. Task records live in `$XDG_STATE_HOME/awui/orchestration/tasks.json` (mode 0600, written through a checked temp-and-rename): at most 200, terminal rows pruned after a week, a bounded result each and no transcript — the child's conversation stays in its harness's own session file. Resident identities use `(calling session, purpose)` so owners can reuse "reviewer" without merging sessions. Store `residents.json` retains up to 24 handles and 24 redacted notes each, 4 KiB per note, with checked temp+rename and checked rollback for every write. Credential-shaped text is redacted on read and write (not generic secret detection); neither request arbitrary native ids nor new-model-account switching reaches the harness. All reads and prompts use one actual ChatManager-managed live writer, refuse busy sessions, and never force reset another agent's existing work. An optional delegate `completionGroup` keeps all its results pending until every member is `result_available`, then uses ordinary durable wake batching; no early-group approval semantics is claimed.
 A child's permission mode can never exceed its parent's, and a child shares the parent's working tree. An optional `writeScope` (≤8 project-relative globs) is enforced server-side by the guard (`orchestration/scope.ts`): a pattern holding `..` is refused before anything starts, every settled tool write is judged against the globs (the task's private `<project>/.awui/scratch/<taskId>` always allowed), a harness whose interactive requests are declared is denied before its unsafe write runs, and one that cannot pre-empt is detected and reported as reported-only — never claimed blocked. One chat may make `callsPerMinute` calls a minute (429 `too_many_calls` past it, so a looping agent cannot spin the surface), `orchestration.enabled: false` stops minting tokens altogether, and every number behind the surface — depth, the per-chat and server-wide caps, the wall clock, the wake budget — is a `config.yml` setting one signed-in device can save, with the switch in the Settings dialog. The MCP endpoint is the same surface with the same token: it bounds one message per request (a 512 KB body), keeps no session, refuses the GET stream it never opens (`405`, `Allow: POST`), and answers a refused call inside a JSON-RPC result, so the model reads a code rather than a stack.
- **A chat's delegated tasks** (`GET /api/chats/:id/tasks`, `POST /api/chats/:id/tasks/:taskId/cancel`) are the browser's side of that surface, behind `requireAuth`: the rows are the same bounded views a snapshot carries (no paths, no transcripts), and a cancel is authorized as that chat and refused for a task another chat started (`not_your_task`). They stay reachable with `orchestration.enabled: false`, so a running child can always be stopped from the panel that shows it.
- **Chat link resolution** (`GET /api/chats/link/:key`) is behind `requireAuth`: a signed-in device asks what a deep-link key opens, and the answer names either a live chat's id or the session record (id, harness, workspace id, title) — never a filesystem path. The key is validated against one bounded shape, and a key nothing answers to is a plain 404.
- **Guided PR review** (`GET /api/workspaces/:id/pr-tour?pr=…&regenerate=true|false`) requires `chat.read`, validates a workspace and numeric PR query, and runs fixed-arg `gh pr view`/`gh pr diff` without forwarding credentials. It uses normalized bounded `ToolDiff` data (80 files, 512 KiB raw patch/96 KiB chunk/768 KiB total) rather than rendering untrusted raw HTML. Unsafe/traversal file labels are skipped; `/dev/null` is not a file. Source, tests/generated, then mechanical config/lock order is a reading aid only. At most 16 per-workspace snapshots are in memory, revalidated by head OID on reopen and kept stale until a successful fresh regeneration returns updated diff content. No approval, merge, or provider account operation is performed.
- **PR activity** (opt-in) lives behind `chat.write`: `POST`/`DELETE /api/chats/:id/pr-watch` and `POST /api/workspaces/:id/pr-repair`. Only that chat's native session owns a watch; another session cannot receive its reports. Dedupe uses a durable fingerprint in `pr-watches.json`, not timestamps, with baseline registration quiet and unwatch idempotent. Active polling finishes via the server's shutdown timeout, and stopped clients never start polling by opening the GitHub panel. A repair prompt is the failing run's actual `gh run view <id> --log-failed`, bounded by a visible truncation marker; its transcript remains that harness's own session. `gh` and git credentials never reach the API or browser. (`GET /api/workspaces/:id/github`, `/pr`, `/checks`, `POST .../push`, `POST .../pr`): use existing `gh` and git authentication with bounded args and no credential reads, tokens echoed, or hidden merges. First-push sets upstream on the local branch when absent. A PR is never created implicitly by browsing, and users push explicitly after review.
- **Stacked PRs** (`GET`/`POST /api/workspaces/:id/pr-stack`, `POST .../pr-stack/:stackId/merge`, `DELETE .../pr-stack/:stackId`): the stack record lives in `$XDG_STATE_HOME/awui/pr-stacks.json` (0600, through the checked temp+rename write): at most 50 stacks of at most 12 layers, each row keeping only PR numbers, URLs (https only), branch names, and the checks' parsed buckets — never a path outside its project (a hand-edited row naming another project drops out on load). Stacking runs the same bounded `gh pr create`/`gh pr view`/`gh pr merge` the panel already runs; the checked-out branch is pushed only when the request's own `push` flag says so, and a merge merges one PR per layer with `--merge` — no rebase, no squash, no branch deletion of our own (deletion is GitHub's, when the repository asks). A merge runs one at a time per project, a refusal stops it with the merged layers persisted, and an archive through the merge goes through the managed worktree's own clean-tree and identity checks below.
- **Live overview** (`GET /api/overview/events`) carries only the status/title/pending/waiting metadata and room summary, not transcripts, output, or harness secrets. Replay is capped; stale readers refresh normal lists. Interactive terminals still use their own scoped event routes.
- **Presence** (`POST /api/presence`): each signed-in web tab reports which chat or room it shows and whether the user visibly sees it, so a notification for a target the user already watches is not sent. It stores a client id, the target id, and two booleans per tab, in memory only (200 clients at most; an entry expires after 60 s without a heartbeat) — no conversation content, nothing written to the state folder. A hidden or unfocused tab keeps reporting, so its chats' notifications still go out.
- **ACP agent settings** (`PUT /api/settings` with `acpAgents`, and `POST /api/settings/acp/test`) are behind `requireAuth` and take a body from a Zod schema. The test runs one handshake with a command that is **already** in config.yml (the browser names an id, never a program), uses that entry's stored environment server-side, and answers with what the agent advertises: never an env value, a path, or the child's stderr (an agent that died is described by its exit code or signal). Its child is tracked under the entry's own id, so testing or shutting one agent down never stops another entry's — or a live chat's — child, even when two entries share a display name. Saving rewrites `harnesses.acp` through `settings.ts`, checked as startup checks it, and a blank env value keeps the stored one, so a device cannot read or clear a secret it was not shown. Both are open to any signed-in device, remote ones included, as every other Settings write is: a device that can save `harnesses.acp` can name a program, which reaches further than a Test of a program config.yml already names, so restricting only the Test would guard nothing. A remote sign-in is the user's own decision, and a remote device reaching the ACP settings reaches them the way it reaches the rest of Settings.

- **Pastes** (`POST /api/chats/:id/pastes`, `DELETE .../:pasteId`) are plaintext under `/tmp/awui-pastes` (0700/0600), limited to 1 MiB, kept for up to seven days because agents may re-read the file on subsequent turns. Draft delete is immediate; expiry uses a daily bounded sweep and a check at consumption. Old or malformed ids never resolve across chats.
- **Usage report** (`GET /api/usage?days=&tz=&refresh=`, 1–365 days) reads the sidebar's sessions active in the range from the harnesses' files, never starting a harness, within a 6-second budget; `refresh=1` bypasses the per-session cache. `GET /api/limits?refresh=1` explicitly polls subscriptions instead of accepting the usual cached reading. Otherwise the report keeps each session's calls in memory per version (600 sessions at most) and returns totals, a day series, the top 12 models, and the top 8 chats.
- **Attribution** (`GET /api/chats/:id/attribution`): reads the chat's edited files as they are now — at most 12 files and 4,000 lines each, through the file viewer's own confinement (only the project's own files, realpath-checked, 512 KB, no link out) — and answers with each line's hash, never its text. The lines' own text never leaves the server here: a client already has it from the tool diffs it draws. A file it cannot read is counted in `skipped` and marks nothing.
- **Side threads** (`POST /api/chats/:id/side`): a question about one turn, asked in a chat awui creates and hides from every session list (`chat.side`, the same reach as a room's ownership). With the Awui harness available that chat is its read-only one (no write or exec tools); otherwise it is a fork of the chat's own session at that turn through the adapter's `forkSession`, so it can do what the chat it came from could — the route says which in its `readOnly` field. The question is at most 2,000 characters and must not be blank, the turn is validated against the chat's own user turns, and the brief is the one-turn budget (20,000 characters, tool output given up first). Nothing is written into the original session file, and the original chat's items are untouched.
- **Second opinions** (`POST`/`GET /api/chats/:id/second-opinion`) send one turn of a chat to another harness: the turn as a bounded first prompt (20,000 characters; tool output given up first), validated against the chat's own user turns, with the target harness checked the way any new chat's is and refused when it is the chat's own. The answer is an ordinary chat in the same project — created through the chat manager, so it holds one live writer and nothing a chat already has — and the records live in `$XDG_STATE_HOME/awui/second-opinions.json` (mode 0600): at most 20 a chat, each with its turn number, harness ids, the chat id, a question of at most 2,000 characters, and the reply's first 2,000 characters, which the list route re-reads from that chat each time rather than storing. A refused prompt disposes the new chat and answers 502. Nothing is written into either harness session file.
- **Free context rotation** (`POST /api/chats/:id/rotate`): starts a fresh session in the chat's own harness from that chat's transcript (the handoff seed: the newest turns word for word, one line per older turn, tool output bounded), and answers with the new chat. It is allowed only while the chat is idle and only where the adapter declares `supportsHandoff`; the adapter writes a new session file through its own store and the old session file is only read, never edited, so this cannot fork or rewrite a harness's history. No model is called and nothing is sent anywhere.
- **The chain** (`PUT /api/chats/:id/chain`): at most 10 steps, each message up to the message limit; a handoff step names an available harness other than the chat's, checked when it is set and again when it runs.
- **A routine's webhook** (`POST /api/hooks/:routineId`): the one `/api` route with no browser session, and it exists only when a routine's own settings carry a hook. It is authenticated by the routine's own secret (HMAC-SHA256 over the raw body, hex, in `X-Awui-Signature` or GitHub's `X-Hub-Signature-256`, compared in constant time) — never by a cookie, and a wrong or missing signature is a 401. A routine id with no hook is a 404, so a scan learns nothing. It is bounded: a 64 KB JSON body, at most 60 deliveries an hour per routine (429 past that), and one run per delivery (a seen delivery id inside ten minutes answers `{ok: true, duplicate: true}`). Whatever a sender's payload becomes is bounded too: at most 4 KB is put where `{{webhook}}` stands in the prompt. What it can reach: it starts that one routine's run — its project, its harness, its prompt — and nothing else; it cannot read, list, or change anything. When it is reachable: whenever awui is, subject to the same Host check as every request, so from another machine only when awui is bound beyond loopback (or fronted) with a password set, and the sender must send an allowed Host. It is off entirely until a routine enables it. Its secret is in `routines.json` (mode 0600) and is returned by `GET /api/routines` to any signed-in device, which can already edit routines — that is, already run prompts on this machine — so the secret is inside the same trust boundary, not a wider one.
- **Routines** (`GET`/`PUT /api/routines`, `POST /api/routines/:id/run`, `DELETE /api/routines/:id`): at most 50, each with a name (80 characters), a prompt (the message limit), a project that must be open, a harness that must be available, and one of the six cadences. A cron expression is checked for meaning (five numeric fields, and a match within a year), a timezone must be one this machine knows, and an expiry must be in the future; each refusal is a 400 naming the problem. A run now answers 202 with the chat it opened, or 409 when the precheck said there was nothing to do. The PUT replaces the whole routine, so the dialog's enable checkbox sends it back with a new flag. `GET /api/routines/runs` reads the run history (bounded: a routine's 20 newest, 200 in all, and a read asks for at most 100), and every verdict there is one bounded line of the agent's own words.
- **Saved prompts** (`GET`/`POST /api/prompts`, `DELETE /api/prompts/:id`) live in `$XDG_STATE_HOME/awui/saved-prompts.json` (mode 0600): at most 200, each name one line of up to 80 characters and unique ignoring case, each text up to 20,000 characters.
- **Review threads** (`GET`/`POST /api/chats/:id/review-threads`, `.../:threadId/notes`, `.../:threadId/status`, `POST .../reanchor`, `POST .../send`, `DELETE .../:threadId`) live in `$XDG_STATE_HOME/awui/review-threads.json` (mode 0600) and never touch a harness's session file: at most 200 threads a chat (a resolved thread is pruned before one is refused, so an open one is never dropped silently) and 50 notes a thread, each note up to 4000 characters. An anchor's path is workspace-relative — an absolute path or any `..` segment is refused — with a line up to 1,000,000 and an 8-hex hash of at most 400 characters of the line's own text; one reanchor call carries at most 200 moves. A send composes the prompt server-side from the chat's stored open threads and refuses past the message limit (413 `prompt_too_long`); it reaches a chat or a new chat of the same project exactly as an ordinary prompt does, so it grants nothing a prompt send already has, and a target that is working takes it as a follow-up where the harness has one or answers 409 `chat_busy`. Only the send needs a live chat: the other routes key on the chat id, so a review outlives the chat being closed.
- **Board rooms** (`/api/bots…`, `/api/rooms…`, and their subroutes) keep bot profiles, rooms, members, the room transcript, and each membership's native-session reference in `$XDG_STATE_HOME/awui/boards/` (0700/0600; a user message is acknowledged only once its record is on disk, and a malformed store is an explicit error, never a silent reset). Routing is server-authoritative: a bare message reaches only the lead, mentions reach exactly the named members (at most 4) in rank order, and a bot may consult only members on its explicit allowlist, one round deep, under per-turn caps (8 invocations, 4 consultations, 3 per member, 180 s wall clock, 20 queued turns; a control document is capped at 16 KiB). Quoted bot output never authorizes anything. A membership's harness session is created and resumed only through the Board manager, and never appears in ordinary session lists, search, usage, or the resume route. Any signed-in device can run bots and spend their providers' quota, exactly as it can already send ordinary chat prompts.
- **File viewer** (`GET /api/workspaces/:id/file?path=`) is read-only and confined to an opened project's own files: the path must be one the project lists (git's tracked files and the untracked ones it does not ignore, else the walk, which skips dotfiles), and its realpath must stay inside the project. It returns the first 512 KB (cut at a line), and no text for a file with a NUL in its first 8 KB.
- **Chat search** (`GET /api/sessions/search?q=`) reads the sessions the sidebar lists, never starting a harness, within a 3-second budget and at most 120 chats; it searches 20,000 characters of each message and 400,000 of each chat, returns three snippets a chat (about 200 characters each), and keeps each session's text in memory per version (400 sessions at most).
- **File list, project search, and session preview** (`GET /api/workspaces/:id/files?q=`, `GET /api/workspaces/:id/search?q=`, `GET /api/sessions/preview`), for the `@` menus, Search in project, atui's history, and the sidebar's hover card, are read-only: the first lists paths relative to an opened project (git's list, else a walk that does not follow symlinks), at most 30 per search; the second runs `git grep` with the query as a fixed string after `-e` (never a pattern or an option), or reads the walk's files of at most 512 KB that are not binary, and returns at most 300 lines, 20 a file, each cut to 240 characters; the third returns a session's last prompt and answer, cut to 400 and 1500 characters, its last model, and the files its edits changed (relative to the project, at most 8), from the live chat or the harness's own file without starting it.
- **Session order and checkouts** (`POST /api/sessions/order`, and `checkouts` in `GET /api/sessions`): an order is at most 500 session ids for one project and harness, and the server keeps the 300 projects arranged most recently; it only orders the list. Each listed project's checkout comes from two read-only git commands run through the hardened runner (`rev-parse --git-common-dir --git-dir`, `symbolic-ref --short HEAD`, 5-second timeout, cached for 30 s); the client gets an opaque repository id and the branch name, never the repository's path.
- **Resume command** (`GET /api/sessions/resume-command`) returns one shell line, the project's folder and the harness's resume arguments, each quoted, on a harness that declares `supportsResumeCommand` and only for a session with a saved file (Claude Code takes only a UUID as the id). It names the plain `claude`, never a configured path (`CLAUDE_BIN`, `harnesses.claude.command`), and nothing of `CLAUDE_CONFIG_DIR`. It runs nothing: the user pastes it into their own terminal. When the session is open in this server, the GET records that line in `$XDG_STATE_HOME/awui/handovers.json` (mode 0600, at most 50, stale after a week) and locks the session: a resume here is refused while no chat is live (409 `session_handed`, unless the client says `reclaim`, which takes the lock), and a normal send to the still-open chat is refused, so two writers meet only by hand. `POST /api/sessions/reclaim` takes the lock and answers the line it held; it is bounded like the resume route and touches nothing on disk but that file.
- **OpenCode's server** listens on `127.0.0.1` only, on a port it picks, behind a 24-byte random password that exists only in its environment and this process; it is never logged or sent to a browser. Its replies are read up to 32 MB and its event frames up to 4 MB.
- **herdr** (`POST /api/herdr/focus`, and the herdr marks in `GET /api/sessions`): the server asks herdr's socket for its agents (one request, answered within a second, a reply of at most 4 MB, read again at most once a second) and switches herdr to a pane only for a request from this machine, since that socket controls herdr's terminals. A pane id must be herdr's shape (`w1:p2`).
- **Queue** (`PUT /api/chats/:id/queue`) replaces a running chat's queued messages (at most 20 of each kind, each within the message limit), only where the harness declares `supportsQueueEdit`.
- Markdown: raw HTML is shown as text, never parsed into elements (no `rehype-raw`). Links are limited to `http`/`https`/`mailto`, and remote images are not loaded.
- Attached images are checked by their magic bytes against the type they claim (PNG, JPEG, GIF, WebP only); only `POST …/messages` accepts a large body (8 × 5 MB), every other route keeps a small limit.
- **Neither Pi nor omp sandboxes itself.** They run as you with their full tool set, and **Tailscale is network access, not a sandbox.** Anyone who can use this UI can make the agent run commands as you.
- **The encrypted relay is a protocol, not a service.** `src/server/relay.ts` (E2's slice) defines an outbound-only tunnel: both sides derive one AES-256-GCM frame key from a one-time pairing secret with HKDF-SHA256, frames are sealed with a fresh 12-byte nonce, and the channel id is itself derived from the key — the relay never sees the secret, the key, or plaintext. The reference relay (`contrib/relay/relay.mjs`, no dependencies) is a zero-knowledge in-memory postbox: it holds ciphertext frames and the frame key's hash only, refuses a wrong hash before any frame moves, sweeps idle channels after 24 h, and is what a person runs on their own machine (`node contrib/relay/relay.mjs`). **No hosted relay ships with awui**; a relay someone else operates would see traffic patterns (timing, sizes) even though the frames are ciphertext. One tunnel, one channel, reconnect by re-handshake; no multiplexing, no inbound port, no key persistence.

## Tailscale

Do this after localhost works:

```bash
# in config.yml: auth.username, auth.password, and allowed_hosts: [<machine>.<tailnet>.ts.net]
npm start
tailscale serve --bg http://127.0.0.1:4783
tailscale serve status
```

`--bg` persists the proxy configuration; it does not start this Node app. Never use Funnel. Open `https://<machine>.<tailnet>.ts.net/` on your phone and sign in; **Pair phone** in Settings lists the addresses.

### LAN (`HOST=0.0.0.0`)

With `host: 0.0.0.0` in `config.yml`, startup prints `LAN: http://<ip>:4783/` for each address. NixOS blocks inbound ports by default, so open it on your LAN interface in the dotfiles, e.g. `networking.firewall.interfaces."enp14s0".allowedTCPPorts = [ 4783 ];` in `hosts/common/firewall.nix`. Prefer Tailscale over exposing it on Wi-Fi you do not control.
